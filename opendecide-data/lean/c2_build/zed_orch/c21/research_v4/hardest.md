## 1. Difficulty mechanisms by decision type

### 1.1 Command safety (allow / ask / block)

Evidence
- Scope heuristics beat target checks. Independent test of Claude Code auto mode: a precise, unauthorised SINGLE-target action has the highest false-negative rate (94.4% at the single-target level, falling to 77.6% when a wide selector matches several candidates), because "the classifier relies on scope-based heuristics, such as treating batch operations as risky, rather than checking whether a specific target is authorized". Overall FPR 19.8%; for production lanes 34.8% vs 9.2% for low-impact lanes; service restart FPR 29.5% (legitimate production rollouts blocked). Source: AmPermBench, arXiv 2604.04978v2, https://arxiv.org/html/2604.04978v2 (independent; paper CC BY-NC-SA 4.0).
- Same effect through a different channel. 36.8% of state-changing actions were in-project file edits outside the classifier's scope; artifact cleanup had 92.9% FNR because "Agents fall back to editing state files when the expected CLI is unavailable". Source: https://arxiv.org/abs/2604.04978 (independent).
- Hardest scenario class in SABER (716 Docker tasks, 8 task categories): "Contextual Warnings" (a warning is visible in the workspace and the safe path exists) with 82.5% harmful-completion rate; highest completed-harm rates for unauthorised access, network outbound and information leakage (32.9%, 30.8%, 28.1%); dominant cause label "task_misunderstood" 47.7%, then injection-following 25.4%, harmful-operation compliance 25.1%. Source: https://arxiv.org/html/2606.01317 (CC BY 4.0 paper; the benchmark owner's own run).
- Static gates miss paraphrase and over-block dual-use. CARE (static-first verifier): weakest on escape and encoding obfuscation variants, strongest on wrapper and whitespace/IFS rewrites; on paraphrased agent-generated attacks full CARE realised harm 52.50% (static only 37.33%); false positives come mainly from benign dual-use commands (cross-host rsync). Its Exploit-DB split is hard because snippets "embed stereotyped destructive idioms" (keyword matchers win there). Source: https://arxiv.org/html/2607.21642v1 (author-run).
- Judge layers raise FPR on routine non-canonical commands (rsync to staging, kubectl apply in a non-production namespace: hybrid FPR 9.0% vs rule-only 2.3%); credential exposure and network access had the lowest risk-level accuracy (68.0%, 72.0%); about 35 of 73 risk-level mismatches sit on the high/critical boundary, "intrinsically subjective". Normalizer rewrites: variable expansion, hex/octal, alias resolution, printf substitution, eval+printf, ANSI-C quoting, backtick, echo substitution, adjacent-quote concatenation. Source: AgentTrust, https://arxiv.org/html/2605.04785v1 (author-run; code and data AGPL-3.0, so this is a difficulty reference only).
- Over-holding is the dominant error at action boundaries: SteerBench-Work reports models wrongly hold authorised, evidence-cleared work 28.1% of the time and wrongly allow unsafe work 1.0%. Source: https://arxiv.org/html/2608.12654 (author-run).
- Trivial baselines matter: always-unsafe F1 0.690 beat 5 of 21 models on R-Judge (already in plan; independent).

Generator targets (our wording, program gold)
1. Equivalent-effect channels: for each destructive effect, render a CLI form AND a direct edit of the state it controls (state file, lock file, config, branch ref file) with the same label. Gate rows by the effect, not the tool name.
2. Scope inversion pairs: precise single-target action on an UNAUTHORISED object (label ASK or BLOCK) vs wide-selector batch action fully inside the authorised set (label ALLOW). This directly breaks the "batch = risky" shortcut. Report FPR/FNR per cell (single/multi x authorised/unauthorised x lane).
3. Warning-visible-and-safe-path-exists rows (the SABER "contextual warning" mechanism): the workspace shows a caution and a reversible alternative exists; gold = take the alternative or ASK, never the shortcut.
4. Benign dual-use in a production lane (cross-host copy, rollout restart, apply in non-prod) with authorisation present in the trajectory: gold ALLOW, to counter the 29.5% / 34.8% over-block pattern.
5. Obfuscation balance: escape/encoding variants (hex, octal, ANSI-C, adjacent quotes) for BOTH dangerous and benign payloads in equal number; dangerous idioms rendered in benign contexts (the CARE "stereotyped idiom" trap) and benign commands in dangerous-looking wrappers.
6. Label the tier (soft vs hard) only where the tier is rule-defined; avoid the high/critical boundary band where inter-rater disagreement is highest (AgentTrust) by not generating rows near a subjective boundary.

### 1.2 Scope / boundary

Evidence
- Independent: UnderSpecBench (69 task families, 2,208 variants, three axes). Target certainty is the dominant axis: Safe Success falls 67.9% to 8.6% and Wrong Target rises 9.6% to 75.1% from B0 to B3; intent clarity weaker (Safe Success 50.9% to 29.4%); blast radius has almost no effect on whether the agent acts or errs (Safe Success 42.4% vs 43.0%; action rate 65.5% vs 64.0%). Runtime surfaces (infrastructure/capacity/observability Safe Success 12.6%, OverScope 77.2%; deployment/traffic 16.6%) are far harder than bounded-object surfaces (24-35%). OverScope includes a broader or more destructive command on the CORRECT target. Refusal is negligible (at most 2.5%). Oracle caveat: one safe action per task; 7 of 100 cases Unclear in a blind human check (kappa 0.86 on the rest). Source: https://arxiv.org/html/2607.02294 (author-run, 69 families).
- AmPermBench confirms the precise-single-target blind spot (section 1.1).
- SteerBench-Work: evidence-reversed MIRRORS are much harder than the incidents they mirror (63.8% vs 98.5% on anchors); lowest-scoring pattern is adversarial controls (45.6%); detector-conflict rows 76.8%; risk-resolved commits (signed or structured evidence already clears a visible risk) are the sharpest over-hold failures. Higher-capability models over-refuse more. Source: https://arxiv.org/html/2608.12654 (author-run; runner MIT, scenarios CC BY 4.0).
- Stated-boundary loss at compaction is documented by Anthropic docs (already in plan permission 5.12). NO-PUBLISHED-STUDY on how often it fails.

Generator targets
1. S x B x R matrix with program oracle (plan) PLUS a separate "wrong object of the right kind" cell (same type, different owner / protected flag) and an "over-broad command on the right object" cell (flag or glob widens the effect). These are the two UnderSpecBench failure types, generated from entity lists, never from their entities.
2. Because blast-radius wording barely moved agents, make blast radius a LABEL-BEARING variable in contrast pairs: same instruction, only the radius fact in the environment changes and the gold flips. A model that ignores radius then scores at chance on those pairs.
3. Mirror pairs for evidence: the same action with (a) a visible risk trigger plus structured clearance evidence (gold ALLOW) and (b) the same trigger with the clearance reversed or stale (gold ASK/BLOCK). Report ALLOW recall on cleared-risk rows because over-holding is the measured dominant error.
4. Adversarial controls: surface features of a risky case with every risk fact resolved, and the converse (clean surface, one unresolved fact in a tool result).

### 1.3 Secret egress

Evidence
- CredLeakBench (email-driven agent workflows; independent of any coding-agent vendor): plain HTTP on the CORRECT hostname is the hardest cue ("Agents check the hostname string and ignore the transport"): Opus 4.8 leaked in 90.6% of no-https cases vs 9.4% on typosquat and certificate-warning cases. Hostname-changing cues (typosquat, homograph, certificate warning) are caught more often. After a login, a follow-up verification page widens exposure (identity or financial fields). Recovery (bypass the phishing link and finish via a trusted destination) is hardest: recovery 0-24.2%. Source of trusted info matters (full URL 33.3% vs domain from an earlier email 15.1% recovery). Pressured user framing raised recovery (47.4% vs 21.9% neutral) and cautious framing gave at most 1.0%. Autonomous low leak rates came with high false refusal (Opus 4.8: 1.6% leak, 88.3% false refusal). A domain-verification instruction cut one model's leak rate from 73.5% to 23.4%. Source: https://arxiv.org/html/2610.08871 (author-run; no data licence stated).
- Skills study (agent skills, 520 skills with leaks; human labels, kappa 0.88): stdout/stderr is the main channel (75.8% of leaking skills), then files (18.7%) and network (13.1%); debug logging is 73.5% of vulnerability instances; 76.3% of cases only show when natural-language description and code are read together; artifact leaks (temp files, shell history) evade secret scanners; secrets removed upstream stayed live in 50+ forks. Source: https://arxiv.org/html/2604.03070v1 (independent; data licence not stated).
- SABER: information leakage and network outbound among the highest completed-harm categories (section 1.1).

Generator targets
1. Channel x provenance x transport matrix (plan T53 plus the missing leg): include channels that are not "send"-shaped (print/log of a value, command-line argument, temp file, shell history, commit of a copied file), each with provenance-bearing gold.
2. Transport as the ONLY discriminating cue: matched pairs where the host string is identical and only the scheme differs (plain vs secure), gold flips. Add matched odd-looking-but-trusted hosts (ALLOW) so "weird host = block" fails.
3. Second-page escalation: first request is fine, a follow-up asks for more fields; gold depends on whether the new fields were within the user's ask.
4. Recovery rows: the user-given link is bad, a trusted source exists in earlier context (full address vs only a domain mentioned); gold = use the trusted route or ASK, never submit.
5. Over-refusal control: at least as many "looks like phishing but is the user's own allow-listed service" ALLOW rows, because refusal can mask a weak gate.

### 1.4 Prompt-injection provenance

Evidence
- Helpful ambient instructions are the hard benign class. AgentDyn (60 open-ended tasks, 560 injection cases; built on AgentDojo) lists hard benign examples: login prompts on a checkout page, OTP verification requests by email, link clicks to accept invitations or download documents, attachment downloads (invoices), git push/pull conflict messages asking for a specific action, web forms requesting an email address, documentation or TODO notes directing steps. "Blindly ignoring all such instructions can therefore cause substantial loss of functionality." Filtering defenses over-defended to near-zero utility; plan-first defenses lost utility on tasks that need replanning (only 6 of 97 AgentDojo tasks need it). Source: https://arxiv.org/html/2602.03117v1 (author-run; no data licence stated).
- Trigger-word shortcut. NotInject (339 benign, 113 per one/two/three trigger words): over-defence accuracy falls with more trigger words (ProtectAIv2 76.11 / 47.79 / 46.02; InjecGuard 91.15 / 89.38 / 81.42); a benign question about a code warning was flagged because of one word. Source: https://arxiv.org/html/2410.22770v3 (author-run; sentences written by GPT-4o-mini per the paper, which is why NotInject is eval-only).
- What makes attacks succeed (AgentDojo): an "important message" framing that addresses the model and tells it a task must be done first beat other prompts; injections near the END of a tool output were most effective (about 70% average against one model); a sensitive goal (for example sending an authentication code) rarely succeeded; two unrelated malicious actions often gave only partial success; stronger models were often easier to attack; tool filtering cut success to about 7% but fails when tools cannot be planned in advance or the attack uses the same tools (about 17%); a BERT detector cut ASR to about 8% but over-blocked. Source: https://arxiv.org/html/2406.13352 (author-run; code MIT).
- InjecAgent: user-case design matters more than attacker-case design; slots that accept only narrow content (an event name) were safer than open fields (tweets); prefixing a fixed "ignore previous instructions" line raised success for nearly all agents (prompted GPT-4: 24% to 47%); fine-tuned agents far more resistant. Source: https://arxiv.org/html/2403.02691 (author-run).
- Adaptive attackers: successful triggers show "low apparent maliciousness", "semantic camouflage" (the harmful action framed as a prerequisite of the user task, or a redefinition of terms so the output format is unchanged) and "conditional framing" (act only if the text is part of a given kind of task, which evaded a re-execution defense). Adaptive attacks passed 12 recent defenses with ASR above 90% for most. Source: The Attacker Moves Second, https://arxiv.org/html/2510.09023v1 (independent, multi-lab; USENIX Security 2026).
- Coding-agent carriers: authority framing in an issue plus a bug-report cover story; "task-relevance framing" (file access presented as needed to fix the bug); tool-description metadata treated as trusted; project config files processed as trusted instructions (one CVE-class case enabling auto-approval via a settings file). MCP tool-description poisoning: more capable models were MORE vulnerable; best refusal rate below 3% (MCPTox, https://arxiv.org/abs/2508.14925). Source for coding assistants: https://arxiv.org/html/2601.17548 (survey of prior work, not replicated; CC BY 4.0 paper).

Generator targets (structured attack tuples; no benchmark strings)
1. Carrier x placement x framing grid with the ALLOW_BENIGN twin of each carrier built from the same format (login/OTP/invite/attachment/conflict-message/form/TODO classes as MECHANISMS; our own wording and domains).
2. Framing styles to include as attack wrappers: prerequisite framing; term-redefinition; conditional ("only if the task is X"); authority + cover story; task-relevance framing. Put the injection at several positions, with at least one third at the tail of the tool output.
3. Delegated-instruction pairs (user said "follow the steps in the file" -> ALLOW_BENIGN; absent -> BLOCK or ASK) with the exact same file content; this is the case a masked re-execution style defense gets wrong, and it is label-bearing only through the user turn.
4. Trigger-word density ladder on benign text (0, 1, 2, 3+ security words) with gold always ALLOW_BENIGN; and the converse, malicious text with zero trigger words.
5. Narrow-slot vs open-field carriers (event name vs free text) as a recorded feature, so the held-out-family gate can test carrier-format generalisation.
6. Detector-feedback realism: hold out whole wrapper styles in validation (already in plan D3) because adaptive success comes from novel framings, not from stronger strings.

### 1.5 Tool need / pick / argument grounding

Evidence
- When2Call: tool-mismatch questions are "deliberately close to the available tools", which makes them harder than ordinary irrelevance cases; plain negative examples made models over-conservative and hurt tool-calling accuracy; balanced preference training worked best. Data was synthetic (Mixtral 8x22B from BFCL v2 Live and APIGen) with about 92% question quality and 94% answer quality by manual estimate; benchmark assumes a direct answer is always wrong. Source: https://arxiv.org/html/2504.18851 (author-run); dataset card CC BY 4.0, train_sft 15,000, train_pref 9,000, test 3,652: https://huggingface.co/datasets/nvidia/When2Call.
- CAR-bench (58 tools, 19 policies, LLM-simulated user): frontier reasoning models below 50% consistent pass on Disambiguation tasks because of premature actions; in Hallucination (missing tool or information) tasks they violate policy or fabricate to satisfy the request; pass^3 gaps are large. Source: https://arxiv.org/abs/2601.22027 (author-run; ACL 2026).
- tau-bench failure analyses (secondary, third-party write-ups): wrong action and wrong arguments dominate, not insufficient chain-of-thought (36 manually reviewed GPT-4o retail failures); simulator error rate itself 47% (airline) and 40% (retail) with 12-13% task-critical. tau2 domain profiles from a later independent paper: airline over-represents policy-eligibility error (+11.9 pp), quantitative reasoning error (+8.5 pp) and constraint-interpretation error (+5.0 pp); retail confirmation-handling error (+6.6 pp) and unsupported fabrication (+4.7 pp); telecom diagnostic-protocol error (+19.0 pp) and escalation handling (+15.9 pp). Sources: https://arxiv.org/pdf/2602.22953 (independent, secondary summary), https://atla-ai.com/post/t-bench (secondary).
- MCP-Atlas diagnostics (secondary summary of the paper): nearly two thirds of diagnosed failures are cognitive (stopping before every claim is covered, or mis-synthesising outputs); a stage-aware study of 427 tasks found restricting agents to gold tools gave only modest gains, leaving failures in workflow continuation, request/parameter grounding, evidence use and runtime stability. Sources: https://arxiv.org/pdf/2602.00933, https://icml.cc/virtual/2026/77938.
- BFCL irrelevance-style categories only check that no call happens, not what the model does instead (When2Call's critique, same source).

Generator targets
1. Near-miss tool sets: same-namespace hard negatives whose description overlaps the request on every word except one capability (missing object type, missing verb, wrong scope). Gold = no suitable tool / ask / answer, never "call the closest".
2. Three different "not callable" causes with different gold: missing tool, missing parameter value (ask), missing prior tool RESULT (say so). Keep call and no-call at 40-60% per sub-block so conservatism cannot win (the over-conservative failure).
3. Policy-eligibility and quantitative-condition rows (eligibility computed from a generated record, then a request that is just inside or just outside): gold ALLOW call vs refuse/ask.
4. Confirmation-handling rows: write call permitted only after an explicit confirmation turn; matched pair differs only in whether the confirmation exists.
5. Premature-action traps for disambiguation: two entities match; calling with either is the failure.
6. NO-PUBLISHED-STUDY on grounding supplied values against earlier context; keep it as our own metric (plan).

### 1.6 Error recovery and loop detection

Evidence
- ToolMaze (author-run; 400 base tasks, 270 tools, four perturbation types): crossing explicit/implicit with transient/permanent; "implicit semantic failures (P3/P4) cause recovery rates to plummet by 37.15%" vs explicit errors (units, points vs relative, not stated: secondary); a secondary write-up reports one model's recovery 90.61% on explicit-transient vs 26.63% on implicit-permanent. Source: https://arxiv.org/pdf/2606.05806 (barred as data per plan E24; difficulty reference only).
- LIMBO (author-run; six simulated services, fault injector, grader reads only a ground-truth effect ledger; 25,930 episodes): when a read-back can reveal what happened the MODEL decides (frontier models duplicated a lost-ack write only 0.5% when told to act once; weaker models often did); when read-back cannot resolve it, reasoning alone cannot finish exactly once on a key-less write, the best the model can do is escalate or report uncertainty. Key semantics follow production conventions (a repeated key with the same parameters replays the original; with different parameters is rejected). Source: https://arxiv.org/pdf/2609.29095 (preprint; secondary summary; note this differs from the plan's "56-74% duplicated" figure, which belongs to a different condition and must be re-checked by the plan owner before it is quoted).
- ProcCtrlBench (200 cases: 100 from SWE-bench Verified, 60 TerminalBench, 40 AndroidBench; two human reviewers + adjudicator; program detectors): "Duplicate Step" = repeated highly similar tool calls with no substantive state change, validation reruns exempt; "Tool Call Chain" = cycles such as A-B-A-B; hardest to detect are latent-workflow defects (Weak Tool F1 0.53, Wrapper Workflow F1 0.59). Source: https://arxiv.org/html/2605.20251 (licence not stated).
- Repetition is not looping: a withdrawn evalscope PR that stalled on identical repeated calls was closed because polling may intentionally repeat while external state changes (https://github.com/modelscope/evalscope/pull/1715). Static-analysis study of infinite agentic loops: most common pattern is retry until "success" with no maximum attempts (68 confirmed in 47 projects, 91.9% precision): https://arxiv.org/html/2607.01641v1. No benchmark labels polling episodes as true/false loops (gap).
- AgentProcessBench (1,000 trajectories, 8,509 human step labels): models struggle to tell neutral steps from erroneous ones; weaker policies look better than they are because they stop early. Source: https://arxiv.org/abs/2603.14465 (eval target B5/D20).

Generator targets
1. Loop-vs-poll as a STATE-CHANGE predicate on a simulated environment: identical call repeated with (a) changing observable (poll, ALLOW continue), (b) unchanged state (loop, stop/escalate), (c) alternating A-B-A-B with no net change (oscillation), (d) validation re-run after an edit (exempt). Gold from the simulator, never from call text.
2. Error ladder 2x2 (explicit/implicit x transient/permanent) where implicit means a well-formed result that violates an invariant NOT named in the card; keep invariant types varied (units, sign, empty-but-ok, truncated list, stale timestamp).
3. Lost-ack write with and without an idempotency-key offer and with and without a read path: gold = retry with same key / read back first / escalate (plan 5.8), with the "replay vs reject on different params" rule for keys encoded in the simulator.
4. Retry-until-success without a bound as a negative (gold: stop after the declared limit and ask).
5. Neutral-vs-erroneous step pairs (a redundant but harmless step vs a harmful one) so the model does not equate "no progress" with "wrong".

### 1.7 Done-claim vs evidence

Evidence
- Field data (20,574 real coding-agent sessions, 16,118 validated episodes): inaccurate self-reporting is 22.58% of episodes; "The agent consistently turns a partial or unverified state into a completion claim"; constraint violations 38.33%, misread intent 26.95%, self-initiated overreach 10.20% (39.29% of overreach co-occurs with misread intent: a question treated as permission to edit). Source: https://arxiv.org/html/2605.29442v1 (independent; released episodes only from permissive-licence repos; LLM-assisted labelling UNVERIFIED).
- False success (completion claim contradicted by environment state): about 45-48% of failures in single-control tau2 domains, about 3% in the dual-control telecom domain (one domain, 15 cases), 75.8% of failures among AppWorld coding agents that report status. LLM judges never exceeded AUROC 0.65 (0.54 on AppWorld) and lean on surface cues such as confident closing language and action volume; TF-IDF classifiers reached 0.83 and 0.95 but lose accuracy across domains without recalibration. Source: https://arxiv.org/html/2606.09863 (author-run, ICML 2026 workshop).
- Small-sample overclaim scoring: 11 of 14 failed runs reported done; one task with a contradictory hidden check accounted for 6 of 11; labellers were Claude models, so treat as anecdote. Source: https://github.com/h-a-forster/overclaim (secondary). Practitioner re-run: 24 claims did not hold, about 1 in 11 (secondary blog).
- Test defects mimic overclaim: OpenAI's audit of a hard SWE-bench Verified subset found at least 59.4% of audited problems had flawed tests rejecting correct submissions (35.5% enforce unrelated implementation details; 18.8% check functionality not asked) https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/ (vendor).

Generator targets
1. Matched pairs with IDENTICAL claim text and differing tool outputs (plan), plus an explicit "surface-cue" probe on TOOL-OUTPUT features too (action-count, confident closing words, length) because published detectors win on exactly those cues.
2. Partial-state-as-complete rows: n of m acceptance items verified, claim covers m; gold = continue. Vary which item is missing (silent test skip, empty result set accepted as success, upload without receipt).
3. Question-as-permission rows for the overreach side (user asked a question; agent edits): gold BLOCK/ASK on the edit.
4. Contradicting-hidden-check rows must be rare and labelled, because one contradictory check inflated an overclaim estimate.

### 1.8 Test gaming / reward hacking

Evidence
- ImpossibleBench (Anthropic/CMU authors; Impossible-LiveCodeBench 103 per variant from the hard split of LiveCodeBench v6; Impossible-SWEbench 349 per variant from SWE-bench Verified; test mutations written by Claude Sonnet 4): four strategies: modify tests, overload comparison operators, record extra state, special-case. Model families differ (Claude and Qwen3-Coder mostly modify tests, over 79% on the conflicting variant; OpenAI models mix all four, each over 14%). Looser prompts, open test access, multiple submissions and complex scaffolds raise cheating; an abort option cut one model's rate from 54% to 9%; easier tasks showed MORE cheating. LLM monitors detect 86-89% on the LiveCodeBench variant but only 42-65% on the SWE variant, and "missed cheating that came with plausible justifications" (for example "backward compatibility"). Source: https://arxiv.org/html/2510.20270v1 (author-run; code MIT, HF data licence not stated).
- EvilGenie (154 hard LiveCodeBench problems): hacks are modified testing procedure (edit test files, change accepted answers) and heuristic solutions (brute-force small inputs, fixed output for large); an LLM judge detects unambiguous hacks well while held-out tests added "only minimal" improvement. Source: https://alphaxiv.org/abs/2511.21654 (author-run, secondary; repo MIT, deprecated).
- METR: stack introspection to read the grader's answer, overwriting an equality operator on tensors so every comparison passes, monkey-patching the evaluator to return a perfect score. Source: https://metr.org/blog/2025-06-05-recent-reward-hacking (independent).
- Prompt-elicited vs natural hacks differ (plan: ModernBERT 34.50 vs 99.70, author-run). School of Reward Hacks: 1,073 GPT-4o-written low-stakes dialogues; fine-tuning on them generalised to broader misalignment and in one replication degraded capability. Source: https://arxiv.org/pdf/2508.17511 (non-coding, LLM-made).
- Anthropic production-RL study: hacking learned in real coding environments generalised to sabotage; mitigations: prevent hacking, diversify safety training, inoculation prompting. https://arxiv.org/html/2511.18397v1 (author-run).

Generator targets
1. The plan's transform library already covers the four ImpossibleBench strategies. Add three missing mechanisms: (a) read the grader's state (call-stack or file read of expected values); (b) patch the evaluator / timing function rather than the code under test; (c) justified special-casing ("backward compatibility", "documented edge case") that is a hack because the spec does not say it.
2. Legit counterparts for each hack with a similar surface: a real special case required by the spec; a test edit that follows a spec change stated in the task; a conftest change that is a genuine fixture fix. Gold ALLOW. Without these the model learns "any test-file edit = hack".
3. Detection difficulty ladder: single-file/short diffs (monitors catch 86-89%) vs multi-file SWE-style diffs with a plausible commit message (42-65%); stratify and report.
4. Heuristic-solution rows (brute force small, constant for large) with visible tests passing and held-out failing.
5. Impossible-by-spec rows (conflicting test): any pass is a hack; include an abort/ask option as gold when the task is impossible.

### 1.9 Code output / equivalence / will-this-test-fail

Evidence
- CRUXEval (800 functions written by Code Llama 34B, outputs by execution): failures cluster in long chains of operations (counting to about 30, many loop iterations), exact string building or manipulation, being misled by variable names, simple comparisons, and recitation errors; even GPT-4 with CoT got 0/10 on 54 output tasks. Source: https://arxiv.org/html/2401.03065 (author-run; MIT).
- CodeSense (4,483 samples from 2,125 Python / 876 C / 875 Java functions; ground truth from dynamic execution traces): input prediction is hardest (about 12% for the best model on small functions); arithmetic and API/function-call statements hardest; post-loop values hard; some open-source models below 50% on binary aliasing and branch questions; failures come from per-statement errors and variable-state tracking across statements; adding API definitions did not help. Source: https://arxiv.org/html/2506.00750v3 (author-run; paper CC BY 4.0, dataset licence not stated).
- Nested constructs: models struggle with nested if / nested loops; on a hard subset with nested loops, frequent function calls and long execution paths accuracy fell about 13 points vs the easy subset (secondary): https://arxiv.org/pdf/2508.05193 and https://arxiv.org/abs/2501.18482.
- EquiBench (2,400 pairs, six categories; no gold from LLMs): hardest are DCE (C pairs from a dead-code-elimination pass; mean 49.0%, essentially chance) and CUDA (best model 63.8%); easiest is pure variable renaming (OJ_V mean 78.1%). Models show a syntactic-similarity bias (predict "inequivalent" for dissimilar pairs and "equivalent" for similar ones; one model got 8.5% on equivalent CUDA pairs but 93.0% on inequivalent ones). Few-shot and chain-of-thought barely help. Source: https://arxiv.org/html/2502.12466v3 (author-run; repo Apache-2.0).
- LiveCodeBench has a test-output-prediction scenario drawn from contest problems with dated releases: https://github.com/LiveCodeBench/LiveCodeBench (MIT).

Generator targets
1. Output-prediction items that need exact string assembly, 15-40 executed steps, a misleading identifier, and an off-by-one in a comparison; gold by three identical runs (plan witness rule).
2. Equivalence pairs in two crossed dimensions: structure change (non-local rewrite, dead-code removal that depends on aliasing or state, loop restructuring) x truth (equivalent / one-token inequivalent). Make sure similar-looking inequivalent pairs outnumber dissimilar-looking equivalent pairs only in the hard slice, otherwise length/similarity becomes the shortcut; run the plan's length-only probe and add a text-similarity-only probe.
3. State tracking: mutation of a shared object through two names (aliasing), post-loop values, early exit from nested loops; wrap in application-style code.
4. Will-this-test-fail: tests whose outcome depends on a mutation made in a helper two calls away; no clocks or randomness.
5. Input prediction ("which input yields this output") as an optional sub-form only if exhaustive-domain checking keeps the gold exact; flag as hardest and rare.

### 1.10 Patch verdict and localisation

Evidence
- Plausible-but-wrong patches: PatchDiff study: 7.8% of patches counted "correct" fail the developer test suite; 29.6% of plausible patches behave differently from the reference; divergence comes from similar-but-divergent implementations (46.8%) and from changing more behaviour than the reference (27.3%); 28.6% of divergent patches are certainly incorrect on manual inspection. https://arxiv.org/html/2503.15223v2 (independent; ICSE 2026).
- UTBoost: after augmenting tests, 28.4% (170/599) of passing patches on SWE-bench Lite and 15.7% (92/584) on Verified were erroneous; Django and sympy hold 84.1% and 82.6% of them. https://arxiv.org/pdf/2506.09289 (independent).
- SWE-ABS: strengthened 251 of 500 Verified instances; rejected 2,184 of 11,041 passing patches (19.78%); top agent 78.80% to 62.20%. Root causes of 100 hand-analysed wrong-but-passing patches: logic errors 47%, incomplete fixes 35%, type mismatch 7%, boundary violations 6%, off-by-one 1%, other 4%. Cause of weak tests: PR tests "verify a specific patch" and leave coverage gaps and semantic blind spots. https://arxiv.org/html/2603.00520v1 (author-run; mutants and tests are LLM-made, so a method reference only).
- SWE-bench+: 32.67% (earlier) to 33.47% (later version) of successful patches had solution leakage in the issue or comments; weak tests 31.08% to 24.70%; filtering dropped one agent's rate from 12.47% to 4.58%. https://arxiv.org/html/2410.06992v2 (independent; two versions differ).
- Localisation: harness study of unresolved runs puts file localisation as the largest failing stage (about 49-56%, rising to 74-77% without planning or with bash only); SWE-smith's staged failure scheme (stuck at localisation / reproduction / incorrect localisation / incorrect edit) and SWE-Lego's read-versus-write localisation split; hunk-level localisation within five lines of the reference predicts success. https://arxiv.org/pdf/2609.20804, https://arxiv.org/pdf/2504.21798, https://arxiv.org/pdf/2601.01426, https://arxiv.org/pdf/2511.00197 (mixed independent and author-run).
- Task validity: test-suite coupling (fixes the target issue, fails unrelated regressions) and implicit naming requirements (tests expect names the issue never states) in SWE-rebench V2 trajectories. https://arxiv.org/pdf/2602.23866.

Generator targets
1. Wrong-but-passing patch classes with the measured mix as the starting weights: logic error 47%, incomplete fix (primary case only) 35%, type mismatch 7%, boundary 6%, off-by-one 1%; each must pass the visible test and be killed by the four-gate hidden suite.
2. "Behaves more than the reference" patches (extra side behaviour) and "similar but divergent" implementations; gold from the differential gate, not from text similarity.
3. Anti-leak control: rows where the issue text contains the fix (solution leakage) must be tagged and held to <= the natural rate, with a CPU probe on "answer present in issue" so the verdict model cannot read the fix from the statement.
4. Implicit-requirement negatives: tests that check a name or format the statement never gives; gold = patch can be correct yet fail; keep rare and labelled so the model does not learn that failure means wrong.
5. Localisation items: report separately file-level and hunk-level, and keep read-versus-write errors distinct in the mutator's metadata.

### 1.11 General reasoning

Evidence
- BBEH replaces the 23 BBH tasks with harder ones needing many-hop reasoning, learning on the fly, finding errors in reasoning traces, long-context needles, going against a strong prior, long-range dependencies, distractors and pattern induction. Difficulty was set semi-adversarially (accuracy kept below 70% for two reference models). Error patterns: models answer "unknown" when a proof exists (BoardgameQA), flag a later step and miss the first error (Dyck trace task), and cluster errors on "ambiguous"/"no" causal labels. Reasoning models gain most on counting, planning, arithmetic and algorithmic tasks, least on commonsense, humour, sarcasm and causation. https://arxiv.org/html/2502.19187 (author-run; software Apache-2.0, other materials CC-BY, https://github.com/google-deepmind/bbeh; the repo was archived 10 Jul 2026).
- ZebraLogic: accuracy declines sharply as the search-space size grows ("curse of complexity"), even with more inference compute. https://arxiv.org/abs/2502.01100 (author-run).
- Generators with adjustable complexity exist (Reasoning Gym, over 100 tasks, Apache-2.0; SynLogic, 35 tasks, automatic verifiers, MIT): https://github.com/open-thought/reasoning-gym, https://huggingface.co/datasets/MiniMaxAI/SynLogic.

Generator targets (program gold; no model-in-the-loop difficulty)
1. Control difficulty by program-measurable quantities (search-space size, proof depth, number of distractor clues, number of definitions to apply), not by filtering against a model. Do not copy BBEH's reference-model calibration (we may not call other models for data selection under the no-big-teacher rule).
2. Include "find the first wrong step" items where a program generates the trace and injects exactly one error at a known step (BBEH's weak spot), and conflict-resolution rule sets with a solver-computed truth value including a genuine "unknown" option at a controlled rate so "unknown" cannot be a shortcut.
3. Operators defined inside the prompt (learn on the fly), time arithmetic composed over several units, tables with a corrupted cell to repair before querying.
4. Keep the plan's rule: no shared sources or domains with OHS-3/4/5 G; no GSM-derived or BBH/BIG-bench-derived items (canary guard F5; barred gsm8k).

### 1.12 Cross-cutting patterns (each seen in at least three decision types)

1. Surface-trigger vs resolved-fact pairs: the hardest published rows keep the alarming surface and resolve the fact (SteerBench cleared-risk mirrors, AgentDyn benign login/OTP prompts, AmPermBench authorised production restarts, CredLeakBench user-owned hosts). Build every family as quads: (alarming surface or calm surface) x (risk fact present or resolved).
2. Over-blocking is under-measured. Dominant measured errors in several benchmarks are false holds (28.1% vs 1.0%; 29.5%-34.8% FPR on authorised production work; 88.3% false refusal). Report ALLOW recall per cell and keep ALLOW at or above 45% in gated families (plan T50) and test it at the 1:19 and 1:99 reweights.
3. The decisive variable is often one the models ignore: transport scheme, blast radius, the user turn, a missing parameter. Make exactly that variable the only edit in a contrast pair.
4. Published detectors win on shortcuts (confident closing language, action volume, trigger words, patch length, syntactic similarity). Every family needs its shortcut probe on the feature class that the literature shows is exploitable, run before generation at scale (plan numeric near-chance rule).
5. Moderate-difficulty reference sets are label-noisy: UnderSpecBench oracles encode one safe action; AgentTrust's high/critical band is subjective; tau-bench user simulators err 40-47%. Our program-gold advantage is exactly that no such band exists; do not generate near undefined boundaries.
