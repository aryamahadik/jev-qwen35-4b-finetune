## 2. Derivations (how the "expected effect" numbers were made)

- Slice-to-family arithmetic: whole-family effect = slice share of the dev set x slice gain. Lever 1: 5% x 6-20 pp = 0.3-1.0. Lever 2: 4% x 10-30 = 0.4-1.2. Lever 3: 2% x 10-25 = 0.2-0.5. Lever 5: 12% x 5-15 = 0.6-1.8. Lever 10: 25% x 1-4 = 0.25-1.0. The slice shares are my choices (a dev slice must be built to see the effect), and the slice gains are guesses anchored on the cited analogies, so each is UNVERIFIED until a pilot reads it.
- Lever 8: routed share 15-25% x gain 1-3 pp = 0.15-0.75 pp. The published gains (3.3-5.3 pp) are for prompted listwise judges; I discount by 40-70% because C2.1 is trained on permuted copies.
- Lever 8 latency: from ALREADY_TESTED_C1_OPT.md, batch 8 gives 9.9 ms per decision, so a batch of 8 takes about 79 ms and batching does not make extra reads free. Fast path 14.1 ms, so one extra read on a routed item is about +14 ms, two extra reads about +28 ms; mean +0.15-0.25 x 14-28 = about +2-7 ms. I report +2..+5 for one extra read.
- Lever 7 ASK rate: if top-1 accuracy is a and coverage target is 1-alpha, the set must add a second option for enough items to recover (a - (1-alpha)) of the probability mass; for a=85%, alpha=10% that is at least 5% of items, at most all 15% errors plus the uncertain correct ones, giving about 5-25% depending on how well probabilities rank the true second option. Measure on mixdev.
- Lever 14 token cut: rows with three or more tool outputs at 256 tokens each carry up to 768 output tokens of an 800 mean; masking all but the last gives roughly 15-35% fewer tokens on those rows. Not measured.
