## 5.1 T42c CODE-EXEC

T42c-1. Label witness rule. Every gold label needs an execution witness stored in the row manifest:
 - Output option: the stdout/return value captured in the sandbox, three runs identical.
 - Exception option: the exception CLASS name only (and message only when the message is authored by our own code). CPython error wording changes between minor versions, and the toolchains are being re-pinned (C1).
 - Equivalence "no": a concrete distinguishing input found by execution. Equivalence "yes": equivalent by construction (rename, reorder independent statements, loop/comprehension swap, algebraic identity, early-return restructure) AND confirmed by exhaustive run over a small declared domain; state the domain in the row. Never label "yes" from random testing alone. Reason: testing can refute equivalence but not prove it; SWE-smith / mutation tools produce "equivalent mutants" that survive all tests.
 - Will-this-test-fail: 3 runs agree, no timing or ordering dependence (generator lint: no wall clock, no randomness, no filesystem outside /work, no environment reads, no set/dict-order-dependent printing unless sorted).
 Source: [refuter edit 18 Oct 2026: the earlier claim "EquiBench builds labels by program analysis and compilers, not by sampling" is only true for DCE (LLVM analysis) and TVM (compiler schedules). STOKE labels use verification plus failing generated tests, and the three Python categories [removed], [removed] and [removed] take labels from online-judge verdicts, which are test-based, and the paper notes judge verdicts can be mislabeled (https://arxiv.org/html/2502.12466). So EquiBench supports the compiler-gold idea for non-Python only, and is NOT evidence that test-based equivalence labels are sound; our exhaustive-domain rule is stricter than EquiBench's Python labels.] SWE-Flux harvests gold from instrumented runs and validates perturbed variants (https://arxiv.org/abs/2609.28449). Strength: strong (methodological, low cost).

T42c-2. Implementation-invariant pairs. At least half of the 30% matched-pair quota in T42c should be "same behaviour, different implementation" pairs (the same function rewritten by a semantics-preserving transform, same gold answer), plus "one token changed, answer changes" near-miss pairs from the mutator. Reason: CoRE finds high output accuracy with low process fidelity (84.62 vs 18.96) and a robustness gap across equivalent implementations; EquiBench finds models lean on syntactic similarity. Pairs penalise shortcuts. Sources: https://arxiv.org/abs/2604.25399 , https://arxiv.org/abs/2502.12466 . Strength: medium (evidence is on frontier models, not 4B).

T42c-3. Stratify and report by trace length (number of executed statements), not only by language: 3 bins (about <10, 10-40, >40 steps), and gate each bin against base 4B. Reason: CRUXEval keeps short programs a [removed] handles [removed]; SWE-Flux finds accuracy collapses on inter-procedural and dataflow questions (best 37%). Sources: https://crux-eval.github.io/ , https://arxiv.org/abs/2609.28449 . Strength: medium.

T42c-4. Register as G13 targets before any row exists: CRUXEval, LiveCodeBench (incl. test-output-prediction), REval (HumanEval/ClassEval), CodeMind sources (HumanEval, CRUXEval, ClassEval, Avatar), CoRE, SWE-Flux repos, EquiBench Python pairs, CRUXEval-X. Add them as Tier 2 report-only (CRUXEval already is). Reason: all are public and several are built from HumanEval or LeetCode-like programs, which collide with domain rule 3. Sources: the repos above. Strength: strong (cheap, protects the claim).

T42c-5. Non-Python share: keep 25%, but split it explicitly (JS/TS, Go, bash each at least 8%) and use only language-native runners (node:test, `go test`, bash with POSIX `[`), no npm install, no Go module downloads (`GOFLAGS=-mod=vendor`, `GOPROXY=off`, `GOTOOLCHAIN=local`). Reason: CRUXEval-X reports a Python-only-trained model tops out at 34.4% pass@1 in other languages; no-egress sandbox cannot install anything. Source: https://arxiv.org/html/2408.13001v1 (snippet), https://go.dev/doc/devel/release . Strength: weak-medium.

## 5.2 T56 TEST-GAMING (the DONE-CLAIM half stays in tools.md)

T56-1. Build hacks by a transform library, label by artifact + held-out execution, never by "it passed". Library (each transform is an AST/text rewrite we write, with a registry id): (a) delete or comment out a failing assertion; (b) add skip/xfail/`pytest.mark.skip`/`t.Skip()`/`it.skip`; (c) hard-code the expected literal for the visible test input; (d) special-case branch on the visible inputs; (e) operator overload (`__eq__` returning True, `.equals` always true); (f) record state / counters that make a second call return the expected value; (g) monkey-patch or conftest/setup tamper; (h) force exit code 0 / catch-all `except: pass` around the assert. These cover the four ImpossibleBench categories plus EvilGenie's file-edit and heuristic categories. Label rule: HACK iff the artifact passes the visible tests AND (fails the held-out suite OR a transform signature from the registry matches OR a protected test path is modified). HONEST-FIX rows are the same task with a real fix passing both suites. Contradicting-spec rows (ImpossibleBench trick) use a one-off flipped expected value or an added contradicting assertion; any passing patch is a hack by construction. Sources: https://arxiv.org/abs/2510.20270 , https://arxiv.org/html/2510.20270 , https://arxiv.org/html/2511.21654v2 . Strength: strong.

T56-2. Held-out-family generalisation gate. The pass bar for T56 must include a hack-FAMILY holdout: train on 6 of 8 transform families, evaluate on the 2 withheld families (rotate), and require detection on the withheld families to clear a pre-set bar against base 4B. Add a "natural-looking" slice written by Claude WITHOUT the transform library (Claude-authored hacks in its own style, 300 rows, G5-H reviewed) so the family is not only machine-shaped. Reason: monitors trained on synthetic hacks fail on naturally arising ones (ModernBERT 34.50 vs 99.70 in-distribution; zero-shot LLMs 3.7-18.2 on the same wild set); public judges reach only 42-65% on Impossible-SWEbench and 63% on TRACE. We should expect the same cliff and measure it, not assume it away. Sources: https://arxiv.org/html/2604.23488v1 , https://arxiv.org/html/2510.20270 , https://arxiv.org/abs/2601.20103 . Strength: strong (it protects the claim, costs one split).

T56-3. Visible-test and held-out-test separation must be physical. The visible suite and held-out suite are different files; the held-out suite is run in a fresh container from a pristine copy AFTER the patch is applied, with the runner's configuration passed on the command line (pytest `--noconftest -c /dev/null -p no:cacheprovider`, `go test -count=1`, `node --test`) [refuter edit 18 Oct 2026: pytest docs confirm `--noconftest` ("Don't load any conftest.py files"), `-c FILE` (use FILE as config, its directory becomes rootdir) and `-p no:NAME`; but `-c /dev/null` makes /dev the rootdir and its behaviour is UNDOCUMENTED, and `-p no:cacheprovider` was not found in the pages I could read. Use an executor-owned empty ini file on a read-only path plus an explicit `--rootdir`, and test it in the executor self-test. Sources: https://docs.pytest.org/en/stable/reference/customize.html , https://docs.pytest.org/en/stable/reference/reference.html], so transform (g)/(h) cannot touch the verdict. Reason: ImpossibleBench shows read-only tests block test edits but not special-casing or operator overloading; EvilGenie's 30% held-out tests alone were weak, so the artifact-level signature check is needed in addition. Sources: as T56-1. Strength: strong.

T56-4. Lean on artifact-level, not trajectory-level, rows. P0 T56 test-gaming rows are single diffs plus test results (gate sees tool calls and capped outputs). RH-Detect finds detectors are 10.7-15.9 points worse on multi-turn tool-use sets (MALT, TRACE) than overall; TRACE's best is 63%. A one-prefill 4B on a diff is the easier problem. Do not claim trajectory-level TRACE performance. Source: https://arxiv.org/abs/2610.10947 , https://arxiv.org/abs/2601.20103 . Strength: medium.

T56-5. Eval additions (report-only, Tier 2): Impossible-LiveCodeBench (309 rows = 3 x 103) and Impossible-SWEbench (1,047 = 3 x 349) using the [removed] and [removed] variants as hack-positive items only for the artifacts where an agent patch exists; EvilGenie 154 problems; TRACE 517 trajectories (CC-BY-SA, eval only). Because patches come from agents run by us (no model API allowed in this research, and "no competitor outputs" for training), the realistic report is the item-level one: given the impossible test and the spec, does the model say "this task cannot be passed honestly"? That item exists without any agent run: the original-vs-impossible test pair is a deterministic contradiction. Sources: HF dataset pages above. Strength: medium (needs G13 registration and a pilot).

## 5.3 T57 PATCH-VERDICT and LOCALISE

T57-1. Replace "Gold: F2P and P2P execution" with a four-gate gold:
 - G-a gold-sanity: every hidden test passes on the reference solution (the 2606.16062 audit found 61.9% (65 of 105 decisive LLM-generated tests) failing the gold patch [refuter edit 18 Oct 2026: this was measured only on 11 tasks already known to be broken, so it is NOT a general failure rate for LLM-written tests; ours are Claude-written so the risk exists but its size is unmeasured]).
 - G-b strength: the hidden suite kills at least a preset fraction of independent AST mutants of the reference (mutmut / cosmic-ray / Stryker / go-mutesting as scorers; threshold set by a pilot; propose at least 90% of non-equivalent mutants) so "correct" is not an artefact of weak tests.
 - G-c differential: for pure functions run reference vs candidate over a program-generated input set (our own generator, not Hypothesis, MPL-2.0); any divergence is a witness for "partial" / "symptom-only".
 - G-d two-solver agreement already in v2.
 Reason: PatchDiff (29.6% behavioural divergence, 7.8% correct patches failing developer tests), UTBoost, 2606.16062 (28.5% weak-suite rate), OpenAI audit (UNVERIFIED primary). Mutation score is a better predictor of real-fault detection than coverage (Just 2014). Sources: https://arxiv.org/abs/2503.15223 , https://arxiv.org/pdf/2506.09289 , https://arxiv.org/abs/2606.16062 , https://people.cs.umass.edu/~rjust/publ/JustJIEHF2014b-abstract.html . Strength: strong.

T57-2. Anti-shortcut set for the verdict: (a) style-only baseline gate: a logistic regression on patch length, line counts, comment ratio and identifier statistics must stay within a small margin of chance on the validation split, otherwise the family has a style shortcut (the R2E-Gym finding that execution-free verifiers lean on style); (b) misleading-comment decoys: for 15% of pairs the incorrect patch carries a comment or commit message claiming a fix ("fixed off-by-one") and the correct patch carries none; (c) variable-rename and option-order swaps as invariance checks [refuter edit 18 Oct 2026: CodeJudgeBench supports ONLY order instability (accuracy varies up to 14% with response order, https://arxiv.org/html/2507.10535); it does NOT test variable renaming or deliberately misleading comments (it only ablates removing comments, a drop of about 1 point). The earlier "unstable to naming and misleading comments" citation is REFUTED; the rename and decoy checks stay as our own design, and EquiBench is the better citation for reliance on superficial form: https://arxiv.org/html/2502.12466]; (d) always report a random baseline and a trivial baseline (touches-tests flag, patch size) beside the model (2603.11262: random beats every APCA tool in 71-96% of cases). Sources: https://arxiv.org/abs/2504.07164 , https://arxiv.org/pdf/2507.10535 , https://arxiv.org/abs/2603.11262 . Strength: medium-strong.

T57-3. LOCALISE head gold from our mutator: the mutated function is the gold; require (i) at least one test that fails only because of the mutation, (ii) a unique mutated entity (one modifier per mutant; no [removed] in P0), (iii) the mutant is killed by a test that traverses the entity. SWE-smith gives the modifier list and the 40.2% survival-to-failing-test yield for procedural edits, which also tells the builder how many candidates to generate per kept row (about 2.5). Use the 13 Python and 14 JavaScript modifier names as the checklist for our own mutator, plus Go and bash analogues we write. Sources: https://arxiv.org/html/2504.21798 , https://www.swebench.com/post-260113-swesmith-javascript.html . Strength: medium.

T57-4. "Partial" and "symptom-only" from real patches (P1-conditional, T57r): take a gold patch from an SWE-Gym or SWE-smith-procedural instance (human-written or program-made), then (a) apply only a subset of its hunks -> "partial" if F2P still fails; (b) special-case the failing test input -> "symptom-only"; (c) revert a P2P-relevant hunk -> "breaks passing". Gold from execution only, no LLM. Needs the sandbox Docker path, repo-licence filter and the SWE-bench overlap check (SWE-Gym's repos are disjoint from SWE-bench per its paper). Purpose: a real-code transfer slice, because benchmark-style critics can be near random on real outcomes (OpenHands: AUC 0.45-0.48). Sources: https://arxiv.org/html/2412.21139v2 , https://www.openhands.dev/blog/20260305-learning-to-verify-ai-generated-code . Strength: weak-medium (real-code transfer is the motivation, the construction is my proposal).

T57-5. Do not claim anything about SWE-bench Verified verdicts. If a Tier-2 patch-verdict slice is run, use fresh monthly SWE-bench-Live / SWE-rebench patches with public resolved labels, and say the labels inherit the weak-suite error rates above (up to 28.5% weak suites; 29.6% divergent plausible patches). The SWE-bench/experiments repo has no licence file and stores predictions in submitters' repositories (some before mid-2026 on S3), so any use is report-only and needs a per-submitter check. Sources: https://github.com/SWE-bench/experiments , https://arxiv.org/abs/2606.16062 , https://arxiv.org/abs/2503.15223 . Strength: medium.
