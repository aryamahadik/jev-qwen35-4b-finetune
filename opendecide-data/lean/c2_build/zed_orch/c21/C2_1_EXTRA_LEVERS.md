# C2.1 EXTRA LEVERS (synthesis of research_v4_levers, Sun 18 Oct 2026; Opus synthesis)

Inputs: the KEPT rows of research_v4_levers/{accuracy, agentic, calibration, robustness, serving}.md (each file had a
refuter pass on 18 Oct 2026; refuter corrections are applied here). Context only: PLAN_TRAINING_SIDE.md v3.1,
ALREADY_TESTED_C1_OPT.md, THINK_MODE_MEASURED.md, OWNER_GOALS_18OCT.md. Rows tagged UNVERIFIED or REFUTED by the refuter
are NOT carried as levers (section 3b lists them). No ohs/sealed path, no Jev output, nothing downloaded, no model run.

How these numbers were made: every "expected" range below is DERIVED (our arithmetic from other models' results). No
source measured a one-token option readout on a fine-tuned Qwen3.5-4B for any of these levers. The closest analogues are
two papers about Qwen3.5-4B decision models from Oct 2026 (LLM2Jev, arXiv 2610.02076; Intern-Decision, arXiv 2610.22131),
and their own authors measured them. Treat every range as a prior to test, not as a forecast.

Rule check (all sections): no lever here uses a bigger teacher, data written by another LLM, eval-set training, sealed
access or a different base. Wording comes from programs or from Claude under the G13 literal ban. Public attack strings
(AgentDojo, BIPIA, InjecAgent, AmPermBench, PAIR) are G13 targets and are never copied. "Own parent" soft targets and
soups use only C1/C2/C2.1, which are our own models.

## 0. Bottom line

1. Nothing new is a big lever on GENERAL accuracy. All ADOPT NOW items together move the G gap to Jev by about
   -0.5 to +0.5 pp (DERIVED). They are hard to see on G anyway: the plan's G SE is 0.40 pp, so a lever needs about
   0.8 pp to show by itself. The G gap still rests on the in-plan levers (public TRAIN splits if A61(b) is approved,
   program-gold general rows, trap selection, alpha blending). The most useful thing this research does for G is
   protection: L23 (length coverage), L13 (adapter attach audit) and clean twins on every robustness row stop silent
   losses of 0.5-2 pp.
2. The real gains are in the coding-agent and security slices. Six new row types (edit-as-action, path aliases,
   late binding, injection aimed at the gate, weak verification, poorly written tool descriptions) cover failure modes
   that published incidents show, and the strongest public gate misses them (AmPermBench, independent: Claude Code auto
   mode FNR 81% on state-changing actions; 36.8% of those actions were file edits that the classifier never sees).
3. Calibration: the plan's ECE <= 3.5% gate does NOT beat Jev under an independent protocol (Rafe and Das,
   arXiv 2610.00346, 29 Sep 2026: Jev 1.13 ECE 3.3% / 3.2% on typed decisions). A "better calibrated than Jev" claim
   needs about <= 2.5-3.0% under that same protocol, or a win on unseen task types (Jev 25.1% shipped there).
4. Latency: kernel levers are worth about 1-4 ms of the 14.1 ms server p50. Of our 137 ms e2e p50, about 100 ms is
   not GPU time. The biggest e2e lever is the hook's process model (S7, -40 to -130 ms per call IF the hook opens a new
   TLS connection on every call, which is unverified).
5. Cost depends on how busy the GPU is, not on kernels. The big cost levers change the model or the product (S19 multi-field
   readout, S17 cascade, S15 batch tier), so they are owner-reserved.
6. Budget: the row-adding levers go in by SUBSTITUTION inside each family's budget, never by taking general rows.
   The long-input tail (A14) is the only one that adds real tokens (+11% at a 5% share, about +$2-3). It is first in
   the shed order if the A37(k) check says the $30 cap binds.
