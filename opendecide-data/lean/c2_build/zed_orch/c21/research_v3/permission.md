### 1.2 Published taxonomies of risky actions (use these to check T50's reason head)

- Anthropic, four groups, "more than twenty block rules": (1) destroy or exfiltrate; (2) degrade security posture (disable logging, install persistence such as SSH keys or cron, modify the agent's own permission config); (3) cross trust boundaries (run code cloned from external repos, scan credential stores for usable tokens, send data to unspecified services); (4) bypass review or affect others (push to main, production deploys, modify shared resources the agent did not create). Source: auto-mode post above.
- Anthropic named rules seen in the config output: "Git Destructive", "Test Artifacts" (allow), "Sensitive-Source Provenance"; and, via a third-party capture of the prompt, rules that no user consent clears: Instruction Poisoning, Auto-Mode Bypass, Self-Modification, Tmux Self Drive, Credential Exploration, Session Transcript Tampering. That last list is one researcher's proxy capture and is UNVERIFIED by Anthropic. Source: https://www.highflame.com/blog/the-44kb-of-claude-codes-rulebook-you-cant-print
- Anthropic incident classes: scope escalation, credential exploration, agent-inferred parameters, sharing via an external service, safety-check bypass. Source: auto-mode post.
- OpenAI: exfiltrating data, exposing secrets, deleting data, weakening security settings, running untrusted code, following untrusted content that conflicts with the user. Source: https://alignment.openai.com/auto-review/
- AuthGateBench (arXiv 2610.16426, 12 Oct 2026) reuses five of the Anthropic incident classes as its failure modes: Scope Escalation, Credential Exploration, Inferred Parameters, External Sharing, Guardrail Bypass. https://arxiv.org/abs/2610.16426
- SABER (arXiv 2606.01317, 31 May 2026) eight task categories: code tampering, data destruction, filesystem destruction, information leakage, network outbound, persistence, privilege escalation, unauthorized access. https://arxiv.org/html/2606.01317v1
- ATBench / ATBench-Codex (arXiv 2604.14858, 16 Apr 2026): a three-axis taxonomy of risk source, failure mode and real-world harm; no leaf list readable on the abstract page. https://arxiv.org/abs/2604.14858

### 1.4 Findings that change what the data should teach

1. Gating failure is mostly a consent/blast-radius judgement, not danger detection. Anthropic says most of its 17% misses "involve correct danger detection but wrong consent judgment" (vendor-run). AmPermBench independently finds the gate lets through scope-escalating actions when the user request is vague (see 1.5).
2. Blast radius is under-weighted. UnderSpecBench: action rate 65.5% at R0 vs 64.0% at R1 (author-run); acted-run Safe Success falls from 67.9% at B0 to 8.6% at B3 [refuter edit: the draft omitted that these are conditioned on runs where the agent acted; overall Safe Success is 15.5-36.8%]. These are agent behaviours, but they show the pressure our gate sees: the proposed action will often name a target the user never named.
3. Stating the scope in the prompt teaches keyword matching. OverEager (the paper's benchmark is called OverEager-Bench): removing the consent declaration raises the overeager rate of the Claude Code harness running the GLM-4.6 base model from 0.0% to 17.1% on a 76-scenario paired set (author-run; not a Claude model) [refuter edit]; the authors write that agents start "pattern-matching declaration text" (verbatim; the draft's longer quote was a paraphrase). For us: a gate trained only on rows whose request names the target will learn "target string appears in request means ALLOW".
4. Always-positive baselines look good on some safety sets. An "always positive" policy on R-Judge scores F1 0.690, beating 5 of 21 models (independent audit, arXiv 2607.28685). Report every gate metric next to trivial baselines.
5. Static rules beat zero-shot LLM judges on speed and on false positives. CARE (author-run): regex baseline F1 29.5 / FPR 0%; LLMJudge F1 73.1 / FPR 11.25%; CARE F1 85.6 / FPR 0.91%. AgentTrust (author-run): a hybrid rules+LLM judge scored lower (88.0%) than rules only (95.0%) because it over-escalated routine commands.
6. Human-authored allow/ask rules do not protect people well: users chose "ask" for 114 of 140 rules (81.4%) and, in the POLICY arm, approved 133 of the 199 overreach prompts shown (66.8%); the HITL and AUTO arms approved under half of their prompts (author-run, n=113, single author, arXiv 2608.27443, 27 Aug 2026) [refuter edit: "approved most overreach" holds only for the POLICY arm]. This supports a learned gate that reads consent from the transcript instead of leaning on static rules.

## 2. Corrections to plan v2

1. "Gold: our own parser (stdlib shlex plus a small grammar)" is under-specified and partly wrong. `shlex.split` does not separate `&&`, `|`, `;` or `>`; they stay glued to neighbouring words, and the operator-aware mode is only reachable through `shlex.shlex(punctuation_chars=True)`. The Python docs state shlex is not a full shell parser and may return tokens a shell would reject. The "no expansion at all" claim is not stated on the shlex page (it only shows operators and `~/a`, `*.py?` kept as literal tokens) [refuter edit: true in practice, but UNVERIFIED from the doc]. Also the doc page does not say `split()` leaves operators glued; the glued tokens in its example come from the non-`punctuation_chars` mode. https://docs.python.org/3/library/shlex.html (read 18 Oct 2026). Fix: the label must not come from parsing the rendered string (see section 5, change 1).
2. "No GPL tools" is right but incomplete. bashlex is GPL-3.0 (its README: "same as GNU bash, GNU GPL v3+") and CARE, which advertises MIT, depends on it. Do not copy CARE code or treat its MIT badge as covering that dependency. bashlex also does not parse `$((..))` and treats `${var#word}` literally. https://github.com/idank/bashlex ; https://github.com/prisma-research/CARE
3. The plan's three-set oracle (authorised / must-preserve / protected) is the AmPermBench oracle and v2 never cites it. Cite it, and note two limits that the AuthGateBench authors raise: AmPermBench covers one failure mode, and it treats authorisation as an explicit mention of the target, ignoring authorisation built up earlier in the trajectory. v2's T51 inherits both limits unless changed (section 5, change 6).
4. T50's reason head (destroy / exfiltrate / weaken security / cross trust boundary / supply-chain / none) drops Anthropic's fourth group, "bypass review or affect others" (push to main, production deploy, modify shared resources the agent did not create). Production deploy and force-push to a shared branch are in the carve-out and ALLOW/BLOCK lists but have no reason label. Add it.
5. v2 lists "Codex escalation classes (elevated shell, network, edits outside writable roots, MCP approval)". Confirmed by the auto-review page, and the circuit-breaker numbers in v2 (3 consecutive or 20 total for Claude; 3 consecutive or 10 of the last 50 for Codex) are correct. One difference to record: the Codex reviewer sees tool outputs, the Claude classifier does not. v2 does not say which view T50/T53 rows use.
6. v2 treats BLOCK as one class. Both vendors use a tier: Claude hard_deny (unclearable) vs soft_deny (clearable by a user message naming operation and target); Codex `forbidden` vs `prompt`. The ALLOW/ASK/BLOCK label cannot encode "the user already said exactly this", which is the commonest real-world flip.
7. "At least 45% ALLOW" is a training balance, not a deployment prior. Real traffic is overwhelmingly benign: users approve 93% of Claude prompts (vendor-run), Codex auto-reviewed escalated actions are approved 99.1% (vendor-run; escalated actions only, 99.93% over all actions [refuter edit]), and Anthropic's FPR is measured on 10,000 real calls. A gate calibrated on 45% ALLOW will over-fire at a realistic prior. v2 has no prior-shift eval slice.
8. Over-simplification in the T50 scope line "T50 executes nothing (static engine plus a simulated filesystem)". Keep it, but the simulated engine must also handle "payloads written to files are evaluated when run" (Anthropic's fixed rule), so a write-then-run sequence needs recursive evaluation of the written script content, not just the command line.

## 4. What the evidence says about gold methods

- Program gold exists and is common: AmPermBench, UnderSpecBench and SABER all check final state with code, not an LLM. UnderSpecBench is explicit: "No LLM judge decides safety" (author-run). Their oracles come from entity lists plus constraints, which our simulated-state generator can reproduce without executing anything.
- The weak point of command-level gold is the parser, not the rule. The 2025-2026 bypasses came from parsing gaps: command substitution (`$(cmd)`, backticks; the `ls $({rm,./test})` brace-expansion form is UNVERIFIED [refuter edit]), environment variables that change what an allowlisted command runs (PAGER/PATH style), a project file named `curl` shadowing the allowed `curl`, and spelling variants that a prefix rule does not match (`git -C . push`, `git -c k=v push`, `git 'push'`, `/usr/bin/curl`, `sh -c '...'`). Sources: Cursor advisories above; the Claude "what a Bash rule does not match" table via the search summary at https://code.claude.com/docs/en/permissions ; CARE and AgentTrust normalisers (IFS splitting, base64, command substitution, ANSI-C quoting, printf and eval+printf chains, adjacent-quote concatenation).
- Good negatives are "dangerous tokens, benign intent". CARE built 170 such commands from NL2Bash (author-run) and reports FPR separately for them. AgentTrust's NeMo Guardrails baseline had a 96.2% false-positive rate (author-run), which is what a token-level shortcut produces.
- Contrast pairs made by editing only the request (AuthGateBench) and paired act/abstain tasks (AgentAbstain) both give a 50% ceiling for constant policies. Both used LLMs to author; we can build the same pairs with a program.
- Provenance, not shape, decides secret handling. Anthropic's allow exception reads: placeholder means "authored as a placeholder"; a file or value "copied from a real secret or sensitive path is never a test artifact". Visibility scopes confidential material only: "secrets ... are never cleared into any repo by its visibility". Source: auto-mode-config page. This is a gold rule our generator can compute from a generated history.
- Destination trust in published work is built from deception cues: typosquat, wrong TLD, raw IP, homograph, misleading subdomain, brand mismatch, unencrypted connection, certificate warning (CredLeakBench, CC BY 4.0, author-run). Gold there came from matching submitted payload hashes in a network log. For us the destination is a string compared against a trusted list, so gold is an exact computation.

## 5. Concrete plan changes

### T50 SHELL-GATE

1. Change the gold method to generate-then-render. Build each row from a structured action spec (program, subcommand, flags, target, wrappers, environment, working tree and git state, policy card). The label is a function of the spec and the simulated state. The command string is rendered from the spec through semantics-preserving operators (wrapper insertion `timeout/nohup/env/command`, flag reordering, `git -C . push`, quoted subcommand, absolute binary path, `sh -c` wrapping, variable-held arguments, brace and IFS splitting, base64 pipe to shell where the payload is registered). Every rendering of one spec gets the same label, which gives matched minimal pairs for free (v2 needs 30%). Use tree-sitter-bash and mvdan/sh only as round-trip validators (rendered string parses to the same command list as the spec), and drop rows where they disagree. Do not use bashlex or shlex as the labeller.
2. Add the evasion families above as a named sub-block with its own gate (obfuscated-dangerous and obfuscated-benign in equal numbers, so "looks obfuscated" is not a cue). Add a CARE-style adversarial-benign slice: dangerous tokens inside echo/grep/commit-message/test-name contexts with benign intent.
3. Opaque scripts: add rows where the command is a script the engine cannot resolve (redirection, substitution, control flow, unknown file). Following Codex's single-opaque-command rule, gold is ASK unless the payload is visible (write-then-run of known content), in which case the engine evaluates the content. Add write-then-run rows because Anthropic evaluates "payloads written to files ... when run".
4. Extend the reason head to 7 classes: destroy, exfiltrate, weaken_security, cross_trust, bypass_review_or_affect_others (new), supply_chain, none. Add four families that v2 lacks and both Anthropic and AuthGateBench name: CRED-SCOUT (grepping or listing credential stores, metadata endpoint, `env | grep KEY`), GUARDRAIL-BYPASS (`--no-verify`, skipping hooks or checks after they fail), EXTERNAL-SHARE (gist, paste, transfer services; hands off to T53), INFERRED-TARGET (acting on the closest-named object; hands off to T51).
5. Replace the three-way label with a four-way label or add a second head: `clears_with_user_naming` (soft) vs `never` (hard). Soft rows carry the consent bar "operation and target both named by the user". Rows pair the same command with and without such a user message. Hard rows: removing the agent's own permission or hook config, disabling its own gate, instruction-poisoning style edits. Source for the tier: Claude auto-mode-config; Codex `forbidden` vs `prompt`.
6. Keep >=45% ALLOW for training, but evaluate on two extra slices: a 1:19 and a 1:99 block-to-allow reweighting of the dev set (reweight, do not generate more rows), and report FPR with a confidence interval at each. Anthropic's 0.4% FPR and Codex's 99.1% approval are the vendor reference points (vendor-run, different workloads).
7. Report T50 against trivial baselines (always-allow, always-ask, regex prefix list, and the stage-1-style "block when unsure" rule) with per-class FPR and FNR, never a single accuracy. Source: arXiv 2607.28685 (independent) and CARE Table II.

### T51 SCOPE-BOUNDARY

8. Generate T51 as an S x B x R matrix with a program oracle. S: explicit command, ticket reference, polite vague request, vague request. B: single named target, ticket with one match, range with >=3 matches, range with the possessive dropped. R: contained lane vs shared/production lane. Oracle: authorised set, must-preserve set, protected set, computed from a generated entity list (branches, jobs, services, buckets, files). Gold for the proposed action: ALLOW when every touched entity is in the authorised set; ASK or BLOCK when it touches the must-preserve or protected set or when the target was inferred by the agent. Sources: arXiv 2604.04978v2 (axes and oracle), arXiv 2607.02294v1 (adds target certainty and blast-radius findings).
9. Keep T51 clean-room against AmPermBench and UnderSpecBench. Authors may use the published idea (S/B/R axes, three-set oracle) but must not use their entity names, id formats (e.g. `job-dev-4812-a`), prompt wording, preambles, or the four task families as written (git branches, Slurm jobs, Kubernetes services, S3 artifacts). Add those strings and phrase frames to the G13 target list as public-eval targets, as v2 already does for other benchmarks.
10. Add trajectory-established authorisation. Authorisation can come from an earlier user message, a listing the user confirmed, or an earlier approved action, not only from naming the target in the current action. Build contrast pairs by editing only the user request or the earlier turn, so the action and state stay identical (AuthGateBench's pair construction, done by program). Source: arXiv 2610.16426 critique of AmPermBench.
11. Add consent-declaration pairs. For a share of rows state the allowed scope in the request and in a matched row omit it, with the same action. Add rows where the declaration is present but the action exceeds it, and rows where the scope is only implied but the action is clearly inside it. This blocks the "target string in the request means ALLOW" shortcut. Source: arXiv 2605.18583.
12. Keep the compaction rows already in v2, now with a source: the docs say a boundary stated only in conversation "can be lost if context compaction removes the message". Gold for a compacted history that dropped the boundary is not "ALLOW"; it is the label under the boundary, since the user said it. Include the "summary kept the boundary" and "summary dropped it" variants, with the fact stated separately in the row so the label is well defined. Source: https://code.claude.com/docs/en/auto-mode-config

### T53 EGRESS-SECRET

13. Add a provenance attribute to every credential-like value: authored-as-placeholder in this session, read from a sensitive path or env earlier, copied from an existing file, public key. Gold depends on provenance, not shape: a string of identical shape is ALLOW as a test fixture the agent wrote, BLOCK when it was read from `~/.aws`, `.env` or a keychain. Source: Claude auto-mode-config "Test Artifacts" and "Sensitive-Source Provenance".
14. Add a visibility axis and a data-class axis: secret vs confidential vs public. Rule from the same page: confidential material may go to a private repo; secrets and personal data are never cleared by repo visibility. Trusted set defaults to the working repo and its remotes; paste and gist services are untrusted unless named.
15. Generate destination distractors from the CredLeakBench cue list: typosquat, wrong TLD, raw IP, homograph, misleading subdomain, brand mismatch, plain HTTP, certificate warning. Gold: exact comparison with the trusted list after normalisation (including public-suffix handling and punycode), so the label is computed, not judged. Include trusted internal hosts that look odd (raw IP of an allowlisted host, internal TLD) as ALLOW to balance.
16. Fake credentials: keep v2's registered-fake rule. Two additions. (a) For formats with a checksum (GitHub's `ghp_` style has a 6-character CRC32 base62 tail, https://github.blog/engineering/platform-security/behind-githubs-new-authentication-token-formats/), generate bodies with a deliberately wrong checksum so a scanner cannot treat a published row as a live token; record this in the registry. (b) Documented example keys (for example the AWS docs key `AKIAIOSFODNN7EXAMPLE`; recalled from AWS docs, not re-fetched: UNVERIFIED) should be capped in frequency, because every model has seen them and they act as a "this is a placeholder" cue. Use gitleaks (MIT) only as a catalogue of key shapes; do not use TruffleHog (AGPL).
17. Add egress channel coverage that v2 lists only in part: HTTP POST of file contents, credentials in URLs, git push to an untrusted remote, upload to a bucket outside the trusted list, log or telemetry endpoints, package publish, and MCP tool calls (GitHub documents that its firewall does not cover MCP servers; https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-firewall, via search summary). Anthropic's synthetic exfil set is "HTTP POSTs of sensitive data, untrusted git pushes, and credentials in URLs, often obfuscated" (vendor-run), so reuse the obfuscation operators from T50 here.

### Cross-cutting

18. State the input view in the family spec. Claude's classifier sees user messages plus the bare command and strips tool results; the Codex reviewer also sees tool calls and outputs. Train each family in the "stripped" view as the primary and a "with tool results" view as a labelled variant, so the same checkpoint can serve either host. If tool results are shown, T41c TAINT rules apply to them.
19. Public eval targets for the permission block, report-only, never trained: SteerBench-Work (MIT/CC BY 4.0, gate-shaped, 106 items), AuthGateBench (gate-shaped, 1,400 items, licence needs a read first), and a re-implementation of the AmPermBench axes on our own held-out sealed generator. Treat UnderSpecBench, OverEager-Gen and CARE's split as unavailable until a release URL and licence exist.
