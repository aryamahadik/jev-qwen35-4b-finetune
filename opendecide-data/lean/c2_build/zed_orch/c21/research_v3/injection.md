### 1.1 The "Horizon-Labs 82.2% (vendor)" reference now has a primary source, and it is not vendor-run
- The only source I can find for Horizon-Labs guard-base is an independent single-author preprint: Zhuowen Liu (JAIST), "Passing the Test You Trained On: Re-evaluating Prompt-Injection Detectors for LLM Agents", arXiv 2610.03448v1, 2 Oct 2026, CC BY 4.0. https://arxiv.org/html/2610.03448v1 . Code and score files MIT: https://github.com/lzwhehe/benign-instruction-bench . [independent, preprint, not peer reviewed]
- 15 detectors plus 2 task-aware LLM judges. Benign tool outputs are built by replaying ground-truth tool calls with no LLM (AgentDojo v1.2: 339 benign outputs from 97 tasks, four suites; tau-bench: 1,533 benign JSON outputs from 675 tasks). Injected outputs are labelled by differential replay (output differs from the clean-environment output of the same call).

- Key findings that matter for T41c (all from Liu 2026, [independent]):
  1. Benign tool-output FPR ranges 0 to over 90% across detectors and is NOT predicted by FPR on general text (ProtectAI v2: 3.8% general text, 30.1% on AgentDojo outputs, 66.9% on tau-bench outputs).
  2. Rankings do not transfer between benchmarks (Kendall tau 0.01 between BIPIA and AD-Matched). PIGuard is first on BIPIA (95.1) and 2.1 on AD-Matched.
  3. Format drives FPR: stripping README markup cut PIGuard general FPR 24.6% to 5.6%; removing YAML keys on AD-Matched cut PIGuard FPR 20.0% to 6.7% at similar TPR; Sheltron's explicit tool_result source token cut AD-Clean FPR 28.6% to 10.6% and tau-bench FPR 85.6% to 4.4%.
  4. Giving the user request to a detector is not a free win: Sheltron(+task) AUROC on AD-Matched rose 0.86 to 0.91 but TPR@1% fell 20.1 to 9.0 and tau-bench FPR rose 4.4% to 69.7%.
  5. PIGuard's training split contains 1,116 full BIPIA inputs (65 of 75 text attacks from BIPIA's train half, 31% of clean emails). Overlap with the test half: none. Dropping to test-half moves its BIPIA TPR from 97.9 to 95.1. This is the template for the contamination statement we should make about ourselves.
  6. Limits stated by the author: simulated environments, static attacks (detection figures are upper bounds), no commercial APIs.

### 1.2 A competitor has now been measured as an injection detector by a third party (14 Oct 2026)
- Lan, Kaul, Pandurangan, Sanyal (eBay), "From Detection to Decision: Calibration and Deferral for Prompt-Injection Detection", arXiv 2610.20907v1, 14 Oct 2026, CC BY 4.0. https://arxiv.org/html/2610.20907 . Code and frozen split IDs (MIT): https://github.com/lanqianlong/calibrated-decision-models . [independent]
- Frozen cohort 47,611 examples: TensorTrust 526 attacks; BIPIA 53 benign + 36,075 attacks; NotInject 89 benign; PIDS-Bench v3 5,488 benign + 5,380 attacks (88.2% attack prevalence, so pooled metrics are dominated by BIPIA).
- Jev ("jev-latest", native probability, one fixed prompt-injection question whose wording is not given): AUROC 0.871, FNR@0.5 0.649, FPR@0.5 0.048, ECE 0.541, mean latency 191 ms. PG2-86M calibrated: AUROC 0.757, FNR@0.5 0.932. LLM judge (GPT-5.5): AUROC 0.897, FNR 0.171, FPR 0.130, 3,890 ms. TPR at 1% FPR for the models ranged 0.9% to 12.5% (the page does not say which is which). [EDIT refuter 18 Oct: the paper's Table 2 does say: Jev-native 12.5%, LLM judge 8.4%, PG2-86M 1.2%, PG2-22M 0.9%, on the pooled cohort (42,000 of 47,611 are attacks, BIPIA-dominated). The authors state Jev was run with one fixed prompt and the results have no confidence intervals.] Jev per-dataset ECE: BIPIA 0.660, NotInject 0.045, PIDS-Bench v3 0.167, TensorTrust 0.204.
- Reading: Jev prompted as a generic injection classifier misses about 65% of pooled attacks at 0.5 (mostly BIPIA) and has low FPR on NotInject (Brier 0.009; exact FPR not stated, UNVERIFIED). This is prompt-sensitive and not a tool-output-with-user-task setting, so it is not evidence of how Jev does inside OHS-5 or on AgentDojo. We can only say it in the form: "a third party measured Jev on a pooled cohort; we measure Jev ourselves on our protocol".
- Their finding that deferral helps only if the reviewer is strong (91.9 to 92.6% escalation needed for FNR<=1% for PG2-86M 91.89 / PG2-22M 92.45 / Jev-native 92.55, with system FPR 40.6 to 45.8% on the confirmatory set; [EDIT refuter 18 Oct: the 98.6% "reviewer FPR" is on the reviewer-calibration split, not the confirmatory set, and the authors call these descriptive statistics, not deployment thresholds]) is a warning for how we describe ASK: report an escalation-vs-risk curve, do not present ASK as free recall.

### 1.4 Independent contradiction on the default-threshold numbers
- An independent engineer's benchmark, "buried-injections" (Shastri, 24 Sep 2026; https://github.com/rudratoshs/buried-injections ; read via a Spanish-language article https://ecosistemastartup.com/prompt-guard-2-de-meta-detecta-1-de-ataques-reales-a-ai-agents/ ; [EDIT refuter 18 Oct: the repo README was opened and confirms the headline numbers: 629 AgentDojo cases built from 27 distinct attack goals and ONE attack template, 97 benign tool outputs for FPR, 10 detectors plus a regex baseline, default threshold 0.5 (LLM Guard 0.92), MIT licence, PG2-86M 6/629 caught and 0/97 FP, PG2-22M 0/629 and 0/97 FP. The repo says re-tuning the 86M threshold to 0.003 on held-out domains gave 97-100% per unseen domain at about 5% false alarms, and warns this may partly reflect the shared template. That re-tuned figure is at ~5% FPR on one template, so it is NOT comparable to Liu's 69.4% at 1% FPR on three templates; the two PG2 numbers come from different constructions, not "the same benchmark". Author-run by an individual, README undated, not peer reviewed]), embedded 629 AgentDojo attacks in legitimate tool outputs for 10 open detectors. Prompt Guard 2 86M detected 6 of 629 (1%) at default settings with zero false positives; 22M detected none; ProtectAI v2 and LLM Guard caught 27/27 isolated attacks but only 23% / 20% when buried; Deepset and fmops flagged about 98% of benign traffic. [independent, secondhand article, repo not read; UNVERIFIED in detail]
- Liu's PG2-86M gets 69.4% TPR at 1% FPR on AD-Matched. These agree once you notice that Liu re-tunes the threshold on the benign set and the buried benchmark uses the default 0.5: PG2 ranks injections well and is badly calibrated on tool outputs. Meta's own number (86M: recall 97.5% at 1% FPR English, AUC .998; AgentDojo "APR" 81.2% at 3% utility reduction; 22M: 88.7% / 78.4%) [vendor-run]. [EDIT refuter 18 Oct: only the 97.5/88.7 recall and AUC are from a direct-jailbreak detection benchmark of isolated prompts; the 81.2/78.4 "APR at 3% utility reduction" is an AgentDojo agentic measure on the model card, a different metric (attack prevention at a utility cost) from Liu's TPR at 1% FPR, so the two are not comparable. The card does not separate user-prompt from tool-output scope.] https://huggingface.co/meta-llama/Llama-Prompt-Guard-2-86M
- Consequence: any "TPR at 1% FPR" claim is meaningless unless the threshold source is stated (see section 5, protocol).

## 2. Corrections to plan v2

1. Tier-1 item 3 ("AgentDojo and InjecAgent as detectors: TPR at 1% FPR. Reference: Horizon-Labs 82.2% (vendor)").
   - The 82.2 is [independent] (Liu 2026), not vendor. It is AD-Matched only, with the threshold fitted on the same benign set.
   - The paper does NOT report a standard InjecAgent number. The InjecAgent attacks appear inside tau-bench product names (Horizon 100.0 there). The plan has no definition of "InjecAgent as detector". Define it ourselves (section 5) and say it is our protocol.
   - Weights changed 2026-10-02; pin the revision when quoting.
   - Expectation line "55-80 vs Horizon 82.2 ... a win is not likely": the independent data shows an enormous spread by training data (Sheltron, trained on agent data, is 20.1 on AD-Matched and 95.2 on tau-bench; PG2-86M with no agent data is 69.4 / 57.9; 7-8B task-aware judges are 55-57 / 54-78). I would not pre-state a range for our model; state only that PG2-86M (69.4 / 78.8) and the 7B judges (57-64) are the realistic comparators and Horizon (82.2 / 87.9) the best point.
2. Tier-1 item 4 ("NotInject: over-defence FPR", target "FPR <= 5%").
   - NotInject is 339 benign prompts (113 per trigger-word count, four categories), MIT on Hugging Face. https://huggingface.co/datasets/leolee99/NotInject . It was written by GPT-4o-mini (trigger words filtered by GPT-4o-mini plus three human raters) per the paper https://arxiv.org/html/2410.22770 . Fine for eval, it can never be training data under the owner rule.
   - The published metric is "over-defence accuracy" (share of benign prompts correctly passed): PIGuard 87.32, LakeraGuard 87.61 (older version), GPT-4o 86.73, ProtectAI v2 56.64, PromptGuard (v1) 0.88 [author-run, InjecGuard paper]. So the comparable FPR numbers are about 12.7%, 12.4%, 13.3%, 43.4%, 99.1%. Report both forms. [EDIT refuter 18 Oct: confirmed in arXiv 2410.22770v3 Table 1, but the paper there calls the model "InjecGuard"; the HF card says it was renamed PIGuard "due to some licensing issues", so cite as InjecGuard/PIGuard. "Lakera (older version)" is not confirmed by the page. The same table also lists Llama Guard 3 at 99.71 (a safety classifier, not an injection guard), Llama-2-chat 76.40, Fmops 5.60, Deepset 5.31; the md's list omits the highest value, so do not call 87 the published ceiling. These are author-run (the InjecGuard authors run all of them, including rivals), accuracy over all 339 prompts, user-turn framing.]
   - The prompts are user-turn style, not tool outputs. Report two framings: (a) as the user turn, (b) as a tool-result carrier. Do not mix them.
   - n=339 means a 95% Wilson upper bound under 5% needs at most 9 false positives (my calculation: 9/339 = 2.65%, upper 4.96%). Make the claim rule "upper bound", not "point estimate under 5%".
   - Jev's NotInject FPR is not published (eBay gives Brier 0.009 / ECE 0.045 on an 89-item subset). We would have to measure Jev ourselves.
3. Eval-upstream exclusion list covers "AgentDojo, InjecAgent, BIPIA and ASB: their attack templates". It is too narrow in two ways.
   - Tier-1 builds its benign side from the benchmarks' ENVIRONMENT content (AgentDojo inbox/calendar/bank/slack/travel tool outputs; tau-bench retail/airline JSON; BIPIA email/table/code contexts). T41c benign carriers must not copy those either. Add to G13 targets: AgentDojo v1.2 environment strings and tool schemas, tau-bench data, BIPIA contexts, InjecAgent user cases and tool lists, AgentDyn environments, MSB and MCPTox server/tool lists, LLMail-Inject, NotInject's 113 trigger words and prompts, PIDS-Bench hard-benign prompts, TensorTrust, CodeIPI samples, LogJack payloads.
   - Add MSB, MCPTox, AgentDyn, TRUST-Bench, LogJack, IssueTrojanBench, CodeIPI, LivePI to the "all eval sets registered as G13 targets BEFORE any C2.1 row exists" list, even if they stay Tier-2 or unused.
4. "WASP (non-commercial)": confirmed. Most of WASP is CC-BY-NC 4.0 (repo page https://github.com/facebookresearch/wasp ); only the visualwebarena part is MIT. Keep it out of training and, to be safe, out of any claim.
5. Plan says (B.4) "Benchmark attack strings are banned from all prompts" and the 200-row G13 pilot checks literals. This is necessary but not sufficient: Liu shows detectors fail on SHAPE (format, serialisation, source token), not only on strings. Add structural controls (section 5).
6. Minor: v2's "NotInject FPR <= 5%" and "AgentDojo/InjecAgent TPR about 55-80" in the expectations block sit next to a "G13 literal" ban. Neither number has support from any published decision-model result; they should be stated as hopes, not forecasts, until we have a C2 dev read.

## 5. Concrete plan changes (T41c design deltas and the Tier-1 eval protocol)

### 5.1 T41c data design

D1. Build carriers as MINIMAL PAIRS.
- For each carrier, program-generate the benign artefact first (README, issue, CI log, tool JSON, MCP description, code comment, rules file). The malicious twin is the same artefact with one Claude-authored payload spliced in at a sampled position. The benign twin is the training row labelled ALLOW or ALLOW_BENIGN; the twin with payload is BLOCK or ASK by rule.
- Why: Liu shows FPR and TPR are dominated by serialisation, markup, and source tokens; pairs make the format uninformative by construction. Also mirrors Liu's own differential-replay labelling, which we can reproduce on Tier-1.
- Gate (cheap, CPU): a format-only probe (logistic regression on carrier-type, serialisation, length bucket, key names, no payload tokens) must be near chance on a held-out split. Fail means the generator leaks format into the label.

D2. Structured attack tuples, not strings.
- Row spec = (user task, authority set, carrier type, carrier format, placement, payload GOAL class, payload WRAPPER style, channel visibility). Claude writes the realised text from the tuple under the G13 literal ban.
- Goal classes already in plan G0/G2 (exfiltrate, destroy, weaken security, supply-chain install, redirect/permission change, persistence hook, resource exhaustion, scope-widening). Wrapper styles: plain imperative, authority framing, urgency, fake system/developer tag, role-play, "pre-authorised step" disguise, conditional trigger, hidden (HTML comment, alt text, zero-width, base64, split across chunks).
- Evidence for the carrier list: IssueTrojanBench (vectors), CodeIPI (issue/comment/README/config), LogJack (cloud and CI logs), AIShellJack (rules files), MSB and MCPTox (tool signature/description/response/retrieval). I read these for taxonomy only; no payload text is copied.

D3. Hold out FAMILIES, not rows.
- Validation split removes whole: 2 wrapper styles, 2 goal classes, 1 carrier format, and 1 placement. Report in-family vs held-out-family accuracy; make a gap above a pre-registered bound (suggest 5 pp) a T41c fix-iteration trigger.
- Evidence: Email-agent paper (random splits overstate robustness); Liu (ranks do not transfer: Kendall tau 0.01 BIPIA vs AD-Matched); AD-Matched (3 templates) vs AD-Shift (5 other templates) is exactly this kind of split and the scores moved 10 to 15 pp for the same detector. [EDIT refuter 18 Oct: REFUTED as written. From Liu's Table 2 the AD-Matched to AD-Shift change is +5.7 (Horizon 82.2 to 87.9), +9.4 (PG2-86M), +10.1 (Wolf), +2.7 (PG2-22M), +6.3 (Sheltron), +7.2 (Prismor); the largest I can read is about 10 pp, and every move is upward (AD-Shift scored higher), not a drop. Also neither set is a train/held-out split for these detectors (the threshold is refit on each set), so this is evidence that template mix shifts scores by up to ~10 pp, not evidence that random splits overstate robustness. The Kendall tau 0.01 (p=1.00) BIPIA vs AD-Matched and the email-agent paper remain the support.]

D4. Four kinds of hard negative (ALLOW_BENIGN), raise benign share and diversify it.
- (a) User-DELEGATED instructions: the user task says "do what the email/issue/README says" and the instruction is in scope. Evidence: all 9 MELON false positives were this kind (arXiv 2502.05174v4).
- (b) AMBIENT HELPFUL instructions on the task's critical path ("install deps first", "run tests with this flag", "log in first"), authored to match the user task. Evidence: AgentDyn builds every case around these and finds defences that block them lose most utility.
- (c) TRIGGER-WORD / security-discussion benign text: imperative or attack-vocabulary content that is benign (security docs describing attacks, CTF write-ups, test fixtures, "ignore this lint rule", roleplay in docs). Evidence: [EDIT refuter 18 Oct: the percentages "technical instructions 30%, security/platform discussion 26%, polysemous words 20%, creative/roleplay 16%" are UNVERIFIED and removed as evidence: the NotInject paper (arXiv 2410.22770v3) as fetched has no such breakdown; it only names four prompt categories (common queries, technique queries, virtual creation, multilingual queries). The category idea stands as our design choice; the source for the numbers is unknown.] Use categories only; none of the 113 trigger words' sentences.
- (d) OFF-TOPIC but benign third-party text (ads, footers, changelog noise, licence headers) so "unrelated to task" does not equal malicious.
- Raise the benign share from ">= 45%" to a target of 50% with at least 30% of the benign rows in (a)+(b), and tag each ALLOW_BENIGN row with its subtype in metadata only (output stays four-way).
- Evidence for diversity over count: PIDS-Bench (enlarging the augmentation pool does not close the gap on external benign text). [EDIT refuter 18 Oct: weaker than stated. PIDS-Bench shows pool SIZE alone does not close the gap; it does not test that diversity does (authors say matched augmentation is untested), and its benign text is user-style prompts, not tool outputs. Treat "diversity over count" as a hypothesis to test with the held-out-family split, not as established.] The email-agent 6/113 to 0/113 result trains on NotInject hard negatives and tests on held-out NotInject items, so it is in-distribution and from a TF-IDF logistic model; qualitative support only. Evidence for including hard negatives at all: Email-agent paper (NotInject-style negatives cut false positives 6/113 to 0/113).
- Label rule by construction: program computes the label from (user-delegated set, task-necessary-and-low-risk set, authority set, action class). In delegated set => ALLOW_BENIGN. Task-necessary and low-risk, not requested => ALLOW_BENIGN. Out of scope or high-risk and unrequested => BLOCK. In scope only with user confirmation, or authority ambiguous => ASK. Opus-approved G0-lite spec must pin the rule table; solver B re-derives labels independently from the rendered row.

D5. Real-text realism without LLM data.
- PIDS-Bench shows detectors fail on externally sourced benign text even when curated hard negatives pass. Claude-authored benign carriers may not match real READMEs/logs. Mitigation, in plan terms: use the P1-conditional vendored permissive repos (MIT/Apache/BSD) as the source of REAL README / CONTRIBUTING / CI-config / comment text for benign twins, with Claude splicing payloads for malicious twins. Needs the pre-mapper 8.5 PASS and per-row licence check already required for that source. If it does not clear, ship T41c with Claude-authored carriers and say the realism gap is untested. (Legal reading of "train on MIT/Apache repo text": UNVERIFIED; the plan already treats this as conditional.)
- For Tier-1 only: Liu's general-text FPR uses GitHub READMEs (h1alexbel/github-readmes), AESLC, FineWeb-Edu. We may report FPR on those as eval, but register them as G13 targets if we vendor any README text.

D6. Carrier length and position.
- The buried-injections result (PG2 86M: 6/629 at default threshold) and BIPIA's start/middle/end insertion say position and surrounding length matter. Add a length tail: about 10 to 15% of rows with 1.5 to 3k-token carriers and a short payload at uniform position; keep the rest short. Check this against the row-length budget before committing (A50/G5 token histogram). If the budget forbids it, say that Tier-1 long-output items will use chunked max-score reads and state it.

D7. Provenance and user task in the prompt.
- Input must carry an explicit source tag for every span (user, system/developer, repo file owned by the user, third-party repo file, tool result, MCP description, MCP response, CI log) and the user task. Evidence: Sheltron's tool_result token cut tau-bench FPR from 85.6% to 4.4% (Liu), and the IH-Challenge hierarchy (system > developer > user > tool). Caution from Liu: adding the task alone did not help Sheltron (TPR@1% fell, FPR rose) because the training data did not teach how the task relates to the carrier, so include task-RELEVANT injections and task-irrelevant benign instructions in training (D4 b, d).
- Keep C2's layout (plan default); put the source tags inside the existing rendered fields rather than re-rendering, to preserve G13/S1 parity records.

D8. Size.
- Keep plan sizes (2,000 / 3,000). I found no evidence that more rows help; I found evidence that composition does. Weak: no change in count.

### 5.2 Tier-1 eval protocol (replace items 3 and 4 text)

P-A. Harness: reuse Liu's MIT scripts to rebuild AD-Clean, AD-Matched, AD-Shift, TB-Clean, TB-Matched, BIPIA test-half and the general-text benign set, with PYTHONHASHSEED=0.
