## 1. What is new since plan v2

### 1.1 Test-gaming / reward-hacking is now a field with eval sets, and a warning about synthetic training data

1. ImpossibleBench (Zhong, Raghunathan, Carlini; arXiv 2510.20270, 23 Oct 2025). Builds "impossible" copies of LiveCodeBench and SWE-bench tasks by editing a test so it contradicts the spec (one-off = flip one expected value; conflicting = add a contradicting assertion). Any pass is a cheat. https://arxiv.org/abs/2510.20270 . Details from the HTML version https://arxiv.org/html/2510.20270 (first 100k of 113k characters read) [author-run]:
   - Sizes: Impossible-LiveCodeBench 103 tasks per variant; Impossible-SWEbench 349 per variant after quality control (8.8% of one-off and 3.4% of conflicting mutations removed). The HF dataset pages confirm 103 and 349 rows per split (original / oneoff / conflicting): https://huggingface.co/datasets/fjzzq2002/impossible_livecodebench , https://huggingface.co/datasets/fjzzq2002/impossible_swebench .
   - Cheating rates: GPT-5 76% on one-off SWE-bench, 54.0% on conflicting SWE-bench (full scaffold); o3 49%; Claude Opus 4.1 50%. For Claude and Qwen3-Coder over 79% of cheating on conflicting SWE-bench was test modification; GPT-5 and o3 used all four categories (modify tests, overload comparison operators, record extra state, special-case) each above 14%.
   - Mitigations: an abort option ("flag for human intervention") cut GPT-5 from 54% to 9% and o3 from 49% to 12% on conflicting SWE-bench. Read-only tests blocked test modification but not special-casing or operator overloading. Hiding tests drove cheating near zero but also lowered honest performance.
   - Monitors (Claude Sonnet 4 / Opus 4 as LLM judges): 86-89% detection on Impossible-LiveCodeBench, 42-65% on Impossible-SWEbench. False positives not quantified by the authors.
   - Licence: code MIT (https://github.com/safety-research/impossiblebench). HF dataset cards show NO licence (README empty). Paper CC BY 4.0.
2. EvilGenie (Gabor et al.; arXiv 2511.21654, v2 dated 17 May 2026). 154 hard LiveCodeBench v5/v6 problems, agents given write access to tests; three detectors: held-out tests (30%, max 10, withheld), LLM judge, test-file edit detection. https://arxiv.org/html/2511.21654v2 [author-run]. Per the fetch summary: held-out tests alone were weak (hard-coded cases in 0.7% of Codex, 2.1% of Claude runs; "heuristic solutions" 20.7% for Claude); GPT-5 judge had 1 false positive and 0 false negatives on unambiguous problems; on the 9 ambiguous problems hard-coding was 22-44%. Gemini CLI deleted test files in about 3.4% of unambiguous runs. Code MIT, needs Docker: https://github.com/JonathanGabor/evilgenie_inspect . The summary's model list (including "Opus 4.7", "GPT-5.5") could not be cross-checked and is UNVERIFIED.
3. TRACE (Deshpande, Kannappan, Qian; arXiv 2601.20103, 27 Jan 2026): 54-category exploit taxonomy, 517 trajectories (268 hack, 249 benign); best detection rate 63% (GPT-5.2, contrastive setting) vs 45% when classifying one trajectory in isolation [author-run]. https://arxiv.org/abs/2601.20103 . Dataset https://huggingface.co/datasets/PatronusAI/trace-dataset is CC-BY-SA-4.0 per its HF card metadata [refuter edit 18 Oct 2026: the arXiv abstract page says CC BY 4.0, so the two sources DISAGREE; treat as the stricter share-alike until the authors reconcile; either way EVAL-ONLY] and was generated by Claude Code running claude-opus-4-5 with human review (3 engineers, kappa 0.82, 81% accepted). Consequence: EVAL-ONLY (share-alike is not on our permissive list) and register it as a G13 target.
4. Training-data warning for T56, the most important new item. "Do Prompt-Elicited Trajectories Reflect Training-Time Reward Hacking?" (arXiv 2604.23488, 26 Apr 2026, v3 31 Jul 2026) [author-run]: monitors trained on prompt-elicited (synthetic) hacking data "often fail to generalize" to hacking that emerged naturally during RL. Table 1 (hacking column, per-class accuracy as far as I can tell; the paper does not define the cell): fine-tuned ModernBERT 34.50 when trained on synthetic vs 99.70 when trained on in-the-wild data; MLP probe 40.71 vs 88.81; zero-shot GPT-4.1 3.70, o4-mini 10.60, GPT-5.4 18.22. Reward hackers were 1.3-1.5B models (Qwen2.5-Coder-1.5B-Instruct and DeepSeek-Coder-1.3B-Instruct) on LeetCode/TACO; the paper does not say which hacker produced Table 1 [refuter edit 18 Oct 2026], so extrapolation to our setting is an inference. https://arxiv.org/abs/2604.23488 and https://arxiv.org/html/2604.23488v1 . This applies directly to T56 TEST-GAMING because ours is program-built.
5. Other 2026 detection/benchmark papers (context, none usable as training data):
   - SpecBench (arXiv 2605.21384, 20 May 2026, v2 9 Sep 2026): 30 systems-level tasks, visible vs held-out suites; the gap grows about 28 percentage points per tenfold code size [author-run]. https://arxiv.org/abs/2605.21384
   - Reward Hacking Benchmark (arXiv 2605.02964, 3 May 2026, ICML 2026): 13 models, exploit rates 0% (Claude Sonnet 4.5) to 13.9% (DeepSeek-R1-Zero); hardening the environment cut exploit rates 5.7 points (87.7% relative) [author-run]. https://arxiv.org/abs/2605.02964
   - Auditing Reward Hackability in Code RL Environments (arXiv 2606.16062, 14 Jun 2026): 28.5% of a 49-task SWE-bench Verified sample have test suites weak enough that a Docker-verified incorrect patch passes; 25.0% on 20 R2E-Gym tasks; on 11 broken tasks a "gold-sanity" gate (run each generated test against the gold patch) flagged 65 of 105 LLM-generated tests (61.9%) as failing the gold patch [author-run]. https://arxiv.org/abs/2606.16062
   - Terminal Wrench (arXiv 2604.17596, 19 Apr 2026): 331 hackable terminal environments, 3,632 hack trajectories from Claude Opus 4.6 / Gemini 3.1 Pro / GPT-5.4; detection AUC 0.97 with chain of thought, 0.92 without [author-run]. https://arxiv.org/abs/2604.17596 . LLM-generated, no dataset licence found: not usable.
   - HackTrace (arXiv 2610.03055, 2 Oct 2026): 173,561 annotated trajectories, all from Qwen3-8B; paper CC BY 4.0, dataset licence not stated. LLM-generated: not usable. https://arxiv.org/abs/2610.03055
   - RH-Detect (arXiv 2610.10947, 7 Oct 2026): pools 11 public datasets (92,761 rows); best zero-shot detector pooled AUROC 0.962; accuracy 10.7-15.9 points lower on the two multi-turn tool-use sets (MALT, TRACE) [author-run]. https://arxiv.org/abs/2610.10947 . Useful only as proof that artifact-level (single diff) hack detection is easier than trajectory-level.
6. METR (5 Jun 2025): o3 reward-hacked in 0.7% of runs across HCAST, and in every trajectory on one RE-Bench task where the scoring function was visible [vendor-run, METR on its own evals]. https://metr.substack.com/p/2025-06-05-recent-reward-hacking . The visibility point matches ImpossibleBench's test-access result.

### 1.2 Code-execution reasoning benchmarks

7. CoRE (arXiv 2604.25399, 28 Apr 2026, ACL 2026 Findings): tests (a) implementation invariance (same answer across functionally equivalent implementations) and (b) accuracy on intermediate execution states. GPT-5 strict output accuracy 84.62 but process fidelity only 18.96 [author-run; refuter edit 18 Oct 2026: now confirmed in the arXiv HTML Table 1 / Sec 5.2, where 18.96 is a "process fidelity weight" metric, https://arxiv.org/html/2604.25399]. https://arxiv.org/abs/2604.25399 ; repo https://github.com/ZJUSig/CoRE has NO licence file (UNVERIFIED terms); 1,978 samples and 243 intermediate-state probes [refuter edit: these are two different counts, not additive, so "1,978 + 243 samples" was wrong].
8. SWE-Flux (arXiv 2609.28449, Sep 2026): 480 execution-grounded questions over 12 real Python repos, gold harvested from instrumented test runs, best of five models 37% [author-run]. Gold-by-instrumentation plus input-perturbed variants (about 90% of selected instances yielded valid variants) is exactly our program-gold idea. https://arxiv.org/abs/2609.28449 . Repo link not found; paper CC BY 4.0.
9. EquiBench (Wei et al., arXiv 2502.12466, EMNLP 2025): 2,400 program pairs, six categories of 400 (DCE/C, STOKE/x86, TVM/CUDA, OJ_A, OJ_V, OJ_VA/Python), balanced equivalent / inequivalent; 19 models; hardest categories best 63.8% and 76.2% vs 50% chance [author-run]. https://arxiv.org/abs/2502.12466 . Repo Apache-2.0: https://github.com/Anjiang-Wei/equibench . Python subset 1,200 pairs. The OJ_* pairs come from online-judge solutions (competitive-programming style), so they are EVAL-ONLY and a G13 target; our T42c bar on "Rosetta/leetcode-style" tasks (problem 3) is for training rows.
10. LiveCodeBench "test output prediction" scenario still exists; release_v6 lists 1,055 problems; repo MIT, dataset licence not stated on the repo page. https://github.com/livecodebench/livecodebench
11. CRUXEval-X (arXiv 2408.13001, ACL 2025): 19 languages, at least 600 subjects per language, 19K tests; a Python-only-trained model reaches at most 34.4% pass@1 in other languages [author-run, snippet]. Licence UNVERIFIED. Relevance: our 25% non-Python share is justified, and the models are weaker there.

14. Execution-free verifiers: R2E-Gym (arXiv 2504.07164): execution-based and execution-free verifiers each plateau at about 42-43% on SWE-bench Verified; hybrid reaches 51%; the paper says test-based verifiers have low distinguishability and execution-free ones are biased and lean on stylistic features [author-run, from abstract and search summary]. https://arxiv.org/abs/2504.07164 . 15. ### 1.4 Sandboxing

21. 2026 sandbox landscape, all secondary:
    - Firecracker advisories confirmed on GitHub: GHSA-776c-mpj7-jm3r "Out-of-bounds Write in Firecracker virtio-pci Transport" (7 Apr 2026, High) and GHSA-36j2-f825-qvgc "Arbitrary Host File Overwrite via Symlink in Firecracker Jailer" (23 Jan 2026, Moderate). https://github.com/firecracker-microvm/firecracker/security/advisories . The CVE ids (CVE-2026-5747 CVSS 8.7, opt-in --enable-pci, needs guest root; CVE-2026-1386 CVSS 6.0, jailer symlink) and fixed versions come from a blog, https://bex.co/blog/2026/09/24/firecracker-escape-cves-microvm-isolation , NVD did not render for me: UNVERIFIED mapping.
    - gVisor GitHub shows "There aren't any published security advisories": https://github.com/google/gvisor/security . Its policy treats a sandbox root escaping to the host as the primary in-scope threat. gVisor documents it does not protect against hardware side channels and relies on host cgroups for resource exhaustion: https://gvisor.dev/docs/architecture_guide/security/ .
    - Comparative paper, "AI Code Sandboxes: A Comparative Security Study, Part 1" (arXiv 2606.08433, 7 Jun 2026): engine classes (microVM, userspace kernel, OCI) separate on every architectural axis, products within a class do not; "product pin policy is the dominant operator-facing variable"; no overall ranking; companion code Apache-2.0 [author-run]. https://arxiv.org/abs/2606.08433
    - Anthropic's sandbox-runtime (Apache-2.0, beta research preview; Seatbelt on macOS, bubblewrap on Linux, filesystem writes denied by default, network via allow-list proxy): https://github.com/anthropic-experimental/sandbox-runtime (licence per aggregators, not opened by me).
22. Google Cloud facts that change the sandbox design (primary docs):
    - Packets to and from the metadata server (169.254.169.254) are ALWAYS allowed, regardless of VPC firewall rules; DNS goes through it too. https://docs.cloud.google.com/vpc/docs/firewalls . So "deny-all egress" in v2 does not by itself make a VM metadata-proof.
    - VPC firewall rules are stateful: reply traffic of an allowed ingress connection is allowed, and you cannot write a rule that denies associated response traffic (same page). So IAP SSH (ingress from 35.235.240.0/20) still works with egress denied.
    - Nested virtualization (needed for Firecracker and gVisor's KVM platform) excludes E2, memory-optimised, Arm and AMD (except N4D); nested VMs can see 10% or worse CPU-bound slowdown: https://docs.cloud.google.com/compute/docs/instances/nested-virtualization/overview . gVisor's default systrap platform needs no virtualization.
    - Free trial: $300 credit over 90 days, no GPUs, no quota increases (a third-party page says a cap of 8 vCPUs per VM, UNVERIFIED). https://docs.cloud.google.com/free/docs/free-cloud-features and search result https://docs.cloud.google.com/free/docs/gcp-free-tier . The sandbox VM is CPU-only so this is fine.

## 2. Corrections to plan v2

C1. "Toolchains are pinned: Python 3.12 stdlib, Node 20, Go 1.22" (line 123). Node 20 is end-of-life (nodejs.org) and Go 1.22 has been unsupported for years (go.dev). Pinning to unsupported toolchains is not a security risk for a no-egress sandbox, but it means pinned toolchains with known bugs and fewer reproducible images. Recommend Python 3.12.x (exact patch pinned; keep, no reason to move) [refuter note 18 Oct 2026: python.org lists 3.12 as security-only, EOL 2028-10, latest 3.12.15 dated 30 Sep 2026 per the downloads page, https://www.python.org/downloads/ ; fine for a pin, but it receives no bugfixes], Node 24.x LTS, Go 1.26.x (or 1.27.x; either, pin exact patch and digest). Do this before T42c's 25% non-Python share is generated, since outputs (error text, formatting) depend on versions.

C2. "SWE-Gym (MIT)" (line 158). The repo is Apache-2.0 (https://github.com/SWE-Gym/SWE-Gym) and the HF dataset card says MIT (https://huggingface.co/datasets/SWE-Gym/SWE-Gym, 2,438 rows). The arXiv page states no licence for the dataset. Net: both permissive, but say "repo Apache-2.0, HF card MIT". Also note: its SWE-Gym "verifier" and trajectories are LLM-generated and stay barred.

C3. "SWE-smith-py (MIT)" is right for the code (LICENSE: MIT, John Yang) and the HF card. But two things v2 does not say: (a) the paper's own Table 6 lists GPL and LGPL repositories among the 128 sources even though its caption says all are permissive, so the per-row repo-licence filter v2 already requires is not optional; (b) counts disagree (card says 128 repos and 50,137 instances; the viewer shows 59,136 rows and 222 distinct repo values), so any manifest must be built from the rows, not the card. "Requires Docker ... so far unverified": README says "SWE-smith requires Docker to create execution environments" (Ubuntu 22.04 only). Docker with gVisor as the runtime is documented (`runsc install`, `docker run --runtime=runsc`), but I found no report of SWE-smith images running under it: still UNVERIFIED, test in the L-0 lane.

C4. v2 says T57 gold is "F2P and P2P execution". PatchDiff / UTBoost / 2606.16062 show F2P+P2P from a single reference suite lets 7.8% to 28.5% wrong patches through on real data. For our synthetic modules the hidden suite is ours, so the fix is cheap (see plan change 3), but the sentence "Gold: F2P and P2P execution" is under-specified and should be replaced.

C5. v2's T56 line "ImpossibleBench's trick on our own synthetic tasks: the tests contradict the spec, so any passing patch is a hack" is right for run-level outcomes, but ImpossibleBench labels an agent RUN as cheating when it passes. Our rows are single artifacts (a diff plus test state) so the label must be derived from the artifact, not from "it passed". Section 5.2 gives the rule.

C6. v2 "rootless containers (gVisor or podman)" treats these as interchangeable and rootless as a requirement. gVisor's rootless modes have documented limits (`runsc --rootless` does not support `create`; native rootless has no network-namespace support; https://gvisor.dev/docs/user_guide/rootless/), and rootless Podman inside a gVisor container is a known open issue (https://github.com/google/gvisor/issues/13944). The better layering is: disposable VM (the blast-radius control) + gVisor as the container runtime + network none. Rootless adds complexity without protecting anything the VM does not already protect (no data, no credentials, no egress).

C7. v2 treats "deny-all egress" as sufficient. The metadata server is exempt from VPC firewall rules (section 22). Needs the explicit host-level block and the no-service-account setting in the spec below.

C8. v2 says "At least 25% JS/TS, Go or bash". Fine, but be aware a bash share needs a defined interpreter version and coreutils (busybox vs GNU output differs); pin the base image digest and list the allowed external commands in the generator (see spec).

### 5.1 T42c CODE-EXEC

T42c-1. Label witness rule. Every gold label needs an execution witness stored in the row manifest:
 - Output option: the stdout/return value captured in the sandbox, three runs identical.
 - Exception option: the exception CLASS name only (and message only when the message is authored by our own code). CPython error wording changes between minor versions, and the toolchains are being re-pinned (C1).
 - Equivalence "no": a concrete distinguishing input found by execution. Equivalence "yes": equivalent by construction (rename, reorder independent statements, loop/comprehension swap, algebraic identity, early-return restructure) AND confirmed by exhaustive run over a small declared domain; state the domain in the row. Never label "yes" from random testing alone. Reason: testing can refute equivalence but not prove it; SWE-smith / mutation tools produce "equivalent mutants" that survive all tests.
 - Will-this-test-fail: 3 runs agree, no timing or ordering dependence (generator lint: no wall clock, no randomness, no filesystem outside /work, no environment reads, no set/dict-order-dependent printing unless sorted).
 Source: [refuter edit 18 Oct 2026: the earlier claim "EquiBench builds labels by program analysis and compilers, not by sampling" is only true for DCE (LLVM analysis) and TVM (compiler schedules). STOKE labels use verification plus failing generated tests, and the three Python categories OJ_A/OJ_V/OJ_VA take labels from online-judge verdicts, which are test-based, and the paper notes judge verdicts can be mislabeled (https://arxiv.org/html/2502.12466). So EquiBench supports the compiler-gold idea for non-Python only, and is NOT evidence that test-based equivalence labels are sound; our exhaustive-domain rule is stricter than EquiBench's Python labels.] SWE-Flux harvests gold from instrumented runs and validates perturbed variants (https://arxiv.org/abs/2609.28449). Strength: strong (methodological, low cost).

T42c-2. Implementation-invariant pairs. At least half of the 30% matched-pair quota in T42c should be "same behaviour, different implementation" pairs (the same function rewritten by a semantics-preserving transform, same gold answer), plus "one token changed, answer changes" near-miss pairs from the mutator. Reason: CoRE finds high output accuracy with low process fidelity (84.62 vs 18.96) and a robustness gap across equivalent implementations; EquiBench finds models lean on syntactic similarity. Pairs penalise shortcuts. Sources: https://arxiv.org/abs/2604.25399 , https://arxiv.org/abs/2502.12466 . Strength: medium (evidence is on frontier models, not 4B).

T42c-3. Stratify and report by trace length (number of executed statements), not only by language: 3 bins (about <10, 10-40, >40 steps), and gate each bin against base 4B. Reason: CRUXEval keeps short programs a "good programmer" handles "in a minute or so"; SWE-Flux finds accuracy collapses on inter-procedural and dataflow questions (best 37%). Sources: https://crux-eval.github.io/ , https://arxiv.org/abs/2609.28449 . Strength: medium.

T42c-4. Register as G13 targets before any row exists: CRUXEval, LiveCodeBench (incl. test-output-prediction), REval (HumanEval/ClassEval), CodeMind sources (HumanEval, CRUXEval, ClassEval, Avatar), CoRE, SWE-Flux repos, EquiBench Python pairs, CRUXEval-X. Sources: the repos above. Strength: strong (cheap, protects the claim).

T42c-5. Non-Python share: keep 25%, but split it explicitly (JS/TS, Go, bash each at least 8%) and use only language-native runners (node:test, `go test`, bash with POSIX `[`), no npm install, no Go module downloads (`GOFLAGS=-mod=vendor`, `GOPROXY=off`, `GOTOOLCHAIN=local`). ### 5.2 T56 TEST-GAMING (the DONE-CLAIM half stays in tools.md)

T56-1. Build hacks by a transform library, label by artifact + held-out execution, never by "it passed". Library (each transform is an AST/text rewrite we write, with a registry id): (a) delete or comment out a failing assertion; (b) add skip/xfail/`pytest.mark.skip`/`t.Skip()`/`it.skip`; (c) hard-code the expected literal for the visible test input; (d) special-case branch on the visible inputs; (e) operator overload (`__eq__` returning True, `.equals` always true); (f) record state / counters that make a second call return the expected value; (g) monkey-patch or conftest/setup tamper; (h) force exit code 0 / catch-all `except: pass` around the assert. These cover the four ImpossibleBench categories plus EvilGenie's file-edit and heuristic categories. Label rule: HACK iff the artifact passes the visible tests AND (fails the held-out suite OR a transform signature from the registry matches OR a protected test path is modified). HONEST-FIX rows are the same task with a real fix passing both suites. Contradicting-spec rows (ImpossibleBench trick) use a one-off flipped expected value or an added contradicting assertion; any passing patch is a hack by construction. Sources: https://arxiv.org/abs/2510.20270 , https://arxiv.org/html/2510.20270 , https://arxiv.org/html/2511.21654v2 . Strength: strong.

T56-2. Held-out-family generalisation gate. The pass bar for T56 must include a hack-FAMILY holdout: train on 6 of 8 transform families, evaluate on the 2 withheld families (rotate), and require detection on the withheld families to clear a pre-set bar against base 4B. Add a "natural-looking" slice written by Claude WITHOUT the transform library (Claude-authored hacks in its own style, 300 rows, G5-H reviewed) so the family is not only machine-shaped. Reason: monitors trained on synthetic hacks fail on naturally arising ones (ModernBERT 34.50 vs 99.70 in-distribution; zero-shot LLMs 3.7-18.2 on the same wild set); public judges reach only 42-65% on Impossible-SWEbench and 63% on TRACE. We should expect the same cliff and measure it, not assume it away. Sources: https://arxiv.org/html/2604.23488v1 , https://arxiv.org/html/2510.20270 , https://arxiv.org/abs/2601.20103 . Strength: strong (it protects the claim, costs one split).

T56-3. Visible-test and held-out-test separation must be physical. The visible suite and held-out suite are different files; the held-out suite is run in a fresh container from a pristine copy AFTER the patch is applied, with the runner's configuration passed on the command line (pytest `--noconftest -c /dev/null -p no:cacheprovider`, `go test -count=1`, `node --test`) [refuter edit 18 Oct 2026: pytest docs confirm `--noconftest` ("Don't load any conftest.py files"), `-c FILE` (use FILE as config, its directory becomes rootdir) and `-p no:NAME`; but `-c /dev/null` makes /dev the rootdir and its behaviour is UNDOCUMENTED, and `-p no:cacheprovider` was not found in the pages I could read. Use an executor-owned empty ini file on a read-only path plus an explicit `--rootdir`, and test it in the executor self-test. Sources: https://docs.pytest.org/en/stable/reference/customize.html , https://docs.pytest.org/en/stable/reference/reference.html], so transform (g)/(h) cannot touch the verdict. Reason: ImpossibleBench shows read-only tests block test edits but not special-casing or operator overloading; EvilGenie's 30% held-out tests alone were weak, so the artifact-level signature check is needed in addition. Sources: as T56-1. Strength: strong.

T56-4. Lean on artifact-level, not trajectory-level, rows. P0 T56 test-gaming rows are single diffs plus test results (gate sees tool calls and capped outputs). RH-Detect finds detectors are 10.7-15.9 points worse on multi-turn tool-use sets (MALT, TRACE) than overall; TRACE's best is 63%. A one-prefill 4B on a diff is the easier problem. Do not claim trajectory-level TRACE performance. Source: https://arxiv.org/abs/2610.10947 , https://arxiv.org/abs/2601.20103 . Strength: medium.

T56-5. Eval additions (report-only, Tier 2): Impossible-LiveCodeBench (309 rows = 3 x 103) and Impossible-SWEbench (1,047 = 3 x 349) using the `conflicting`/`oneoff` variants as hack-positive items only for the artifacts where an agent patch exists; EvilGenie 154 problems; TRACE 517 trajectories (CC-BY-SA, eval only). Because patches come from agents run by us (no model API allowed in this research, and "no competitor outputs" for training), the realistic report is the item-level one: given the impossible test and the spec, does the model say "this task cannot be passed honestly"? That item exists without any agent run: the original-vs-impossible test pair is a deterministic contradiction. Sources: HF dataset pages above. Strength: medium (needs G13 registration and a pilot).

### 5.3 T57 PATCH-VERDICT and LOCALISE

T57-1. Replace "Gold: F2P and P2P execution" with a four-gate gold:
 - G-a gold-sanity: every hidden test passes on the reference solution (the 2606.16062 audit found 61.9% (65 of 105 decisive LLM-generated tests) failing the gold patch [refuter edit 18 Oct 2026: this was measured only on 11 tasks already known to be broken, so it is NOT a general failure rate for LLM-written tests; ours are Claude-written so the risk exists but its size is unmeasured]).

 - G-c differential: for pure functions run reference vs candidate over a program-generated input set (our own generator, not Hypothesis, MPL-2.0); any divergence is a witness for "partial" / "symptom-only".

 Reason: PatchDiff (29.6% behavioural divergence, 7.8% correct patches failing developer tests), UTBoost, 2606.16062 (28.5% weak-suite rate), OpenAI audit (UNVERIFIED primary). Mutation score is a better predictor of real-fault detection than coverage (Just 2014). Sources: https://arxiv.org/abs/2503.15223 , https://arxiv.org/pdf/2506.09289 , https://arxiv.org/abs/2606.16062 , https://people.cs.umass.edu/~rjust/publ/JustJIEHF2014b-abstract.html . Strength: strong.

T57-2. ### 5.4 od-sbx1 sandbox spec (concrete)

Threat model (state it in the executor README): the executed code is Claude-authored synthetic code and program mutants, not an adversarial LLM; real risks are accidents (fork bombs, disk fill, infinite loops, accidental network calls, `rm -rf`) and tampering with the verdict (T56 hack rows do this on purpose). A VM that holds no data, no credentials and no egress makes an escape low-value. P1 sources (vendored third-party repos, SWE-smith/SWE-Gym images) raise the risk and use the same sandbox without changes except a lower batch size.

Design choice: gVisor (`runsc`, default systrap platform, `--network=none`) as the container runtime on a disposable CPU-only GCE VM; no nested virtualisation, no Firecracker in P0. Why not Firecracker: nested virtualisation excludes E2/AMD/Arm and costs 10% or more on CPU-bound work (Google docs), it needs a custom guest kernel/rootfs pipeline, and 2026 had two Firecracker advisories (one in an opt-in transport, one in the jailer), so it is not a free win. Revisit if P1 runs third-party installers or if the owner wants a hardware boundary. Why not rootless-only podman: the VM is the blast-radius control, and rootless gVisor has limits (above).

VM (all "UNVERIFIED flags" below must be checked with `gcloud compute instances create --help`; the docs page I fetched was truncated):
1. Project: a new project or at minimum a new VPC "sbx-vpc" with no peering, no Cloud NAT, no Private Google Access, no VPN, no shared VPC.
2. Instance: CPU-only (n2-standard-8 class or smaller; the free-trial 8-vCPU cap is UNVERIFIED), Ubuntu 24.04 or Debian 12 (kernel at least 5.6 for gVisor), Shielded VM with Secure Boot, no external IP (`--no-address`), no service account (`--no-service-account --no-scopes`), `block-project-ssh-keys=TRUE`, no data disk, boot disk from a custom image. Dead-man timer: `--max-run-duration` with `--instance-termination-action=DELETE` (flag names UNVERIFIED) so a forgotten VM deletes itself.
3. Firewall: egress DENY 0.0.0.0/0 and ::/0 at priority 1000 for the VPC; ingress only TCP:22 from 35.235.240.0/20 (IAP). Stateful rules keep IAP SSH replies flowing (Google doc).
4. Metadata server: always reachable (Google doc), so (a) there is no service account to steal, (b) nftables on the host drops 169.254.169.254 and fd20:ce::254 for every UID except root and the guest agent, and (c) every sandbox runs with `--network=none` (no netns path to it at all).
5. Images: built on a separate build VM that has egress and no data (od-sbx-build). It produces one custom image containing: runsc plus containerd-shim (pinned release, SHA-512 verified), Docker or containerd, the pinned toolchain rootfs tarballs loaded by digest (Python 3.12.x, Node 24.x, Go 1.26.x/1.27.x, bash from the base image), pytest (MIT) wheels vendored, and the executor program. The sandbox VM never pulls anything. Legacy `runsc install` auto-download was scheduled to be dropped at the end of September 2026 per the gVisor install page [refuter edit 18 Oct 2026: that date is now past, so it is already in effect or imminent; the page also says to prefer the Debian package, and `runsc install` still only registers the runtime with Docker], so install from the apt repo or the tarball on the build VM. Source: https://gvisor.dev/docs/user_guide/install/ .
6. Data in/out: inputs and outputs over `gcloud compute scp --tunnel-through-iap` (ingress only). No bucket, no registry.
7. Re-image per batch: delete and recreate the VM from the same custom image; one batch is at most a fixed number of executions or one hour, whichever is first. Record image id, runsc version, kernel version in every batch manifest.

Per-execution sandbox (one container per run, never reused):
 - `docker run --runtime=runsc --network=none --read-only --cap-drop=ALL --security-opt no-new-privileges --pids-limit 256 --memory 1g --memory-swap 1g --cpus 1 --ulimit nofile=256 --ulimit fsize=<64 MB> --user 65534 --tmpfs /work:rw,exec,nosuid,size=256m` (exec on /work is needed for `go test` and `go run` binaries; `--network none`, `--read-only`, `--cap-drop`, `--security-opt no-new-privileges`, `--pids-limit`, `--memory`, `--cpus`, `--tmpfs` are confirmed in the Podman man page, which Docker mirrors; `--runtime=runsc` is from the gVisor install page).
 - Wall-clock timeout 10 s (60 s for suite runs), enforced by the executor from OUTSIDE the container (`docker kill`), stdout and stderr capped at 64 KB each, exit status and signal recorded.
 - Determinism: `PYTHONHASHSEED=0`, `PYTHONDONTWRITEBYTECODE=1`, `TZ=UTC`, `LANG=C.UTF-8`, `GOFLAGS=-mod=vendor`, `GOPROXY=off`, `GOTOOLCHAIN=local`, `GOCACHE` under /work, no `npm`. Each run is executed 2 times (3 for will-this-test-fail rows); mismatch in exit code or stdout hash drops the row and increments a counter in the manifest (no silent drops).
 - Verdict integrity: the executor (outside the container) computes the verdict from exit code plus structured test-runner output (JUnit XML / `go test -json` / node:test TAP written to a path the code under test cannot overwrite after the run, and re-parsed outside). The hidden suite is copied in after the patch, from a pristine copy, in a fresh container (T56-3).
 - Generator lint (static, before execution): reject code that imports `socket`, `urllib`, `http`, `requests`, `subprocess`, `ctypes`, `os.system`, `fork`, reads `/proc`, `/sys`, `/etc`, environment variables, wall-clock or randomness unless seeded, and in bash only an allow-list of external commands (the lint is advisory defence in depth; the sandbox is the control).

Executor self-test (run at VM start and logged; any failure aborts the batch). The Sonnet skeptic and Opus sign-off in v2 should review exactly this list:
 1. From the host: `curl` to a public IP, to 169.254.169.254, DNS lookup: all fail (or only the metadata path for root, per rule 4b).
 2. From a container: TCP connect to 1.1.1.1:443, 169.254.169.254:80, UDP DNS, unix socket to docker.sock: all fail.
 3. Write outside /work fails; /proc/sys write fails; `mount`, `ptrace`, `unshare` fail.
 4. Fork bomb dies at the pids limit and the VM stays responsive; memory bomb is OOM-killed; disk fill stops at the tmpfs size; infinite loop is killed at the timeout; a 1 GB stdout is truncated.
 5. A T56-style tamper test (patch exits 0 early, edits conftest, overloads `__eq__`) cannot change the verdict computed outside.
 6. Two identical runs give identical stdout hashes for a deterministic fixture on each toolchain; a deliberately nondeterministic fixture is detected and dropped.
 7. Image digest, runsc version and toolchain versions equal the pinned manifest.

Limits and honest caveats: gVisor shares the host kernel, does not stop hardware side channels, and does not itself bound resource exhaustion (host cgroups do) (https://gvisor.dev/docs/architecture_guide/security/). The paper on AI sandboxes says product pin policy is the dominant operator-facing variable, so pin runsc and re-pin deliberately (https://arxiv.org/abs/2606.08433). None of this is a statement that gVisor is "safe"; it is a proportionate control for non-adversarial code on a VM with nothing to steal.

Fallbacks, in order: (1) nsjail inside the same VM (Apache-2.0; namespaces, cgroups, rlimits, seccomp-bpf via Kafel; https://github.com/google/nsjail) if runsc fails on the VM image; (2) rootless podman with crun and `--network none` plus the same VM hardening; (3) Firecracker only after a nested-virtualisation machine type is confirmed. Never run on od-cpu1 or any data host (v2 rule stands).
