## Design points a reader should know
* **One serving path.** Every model: same image, same command, same pin check, same `path_sha256`; metas carry `host modal`, the H100 name, the SGLang venv's torch / CUDA (one value over the job, as `pipeline_check` demands), `load.{revision, chat_template_sha, forced []}`, `engine sglang`, plus adapter / merge-manifest / grid / data shas.
* **merge_direct vs the production export.** It is not `export_local` (10-25 min per model); it is its arithmetic. **Checked at full scale on this Mac (18 Oct, CPU, 53 s):** `merge_adapter(real Qwen3.5-4B @ 851bf6e8, real C1 adapter 507d1c29)` wrote both shards, the index, config and every other file with sha256 equal to the production export's manifest (`speed/export_c1_merged.json`: c5f526b9..., 979e2e70..., all 17 files EQUAL), 248 targets changed, 24 `norm.weight` rounded, 154 unchanged, 312 vision / MTP copied; the same run found that `A_log` must stay F32 (fixed). Also bound by: a bitwise test against real PEFT `merge_and_unload` on tiny layers, the `ckpt_to_mem` / `BASE_PINS` equality tests, a C1 cross-check against `/vol/models/q35_4b_main500k_merged` when the Volume has one (reported in `block.json`, not fatal), and the parity job for the chosen candidate.
* **Latency (Q6).** One record per candidate against the C1 read of the same job (same server arguments, workload S, batch 1). H100 batch-1 p50 is ~30 ms, so a single-boot ratio against the 1.05 bar carries boot-to-boot noise; the real D9 record for the chosen candidate is still the L4 procedure in `c2_build/serving` (`d9_latency.py`).
* **Money.** Container seconds x rate against one ledger; each model block starts only if spent + elapsed + one model <= 3.60; the laptop cancels at 14.60; `SESSION_TIMEOUT_S` (11,700 s) alone cannot cross 15.00 (tested). `max_containers=1`, `retries=0`, GPU `H100!`, never `--detach`. Image build and GPU queue time are not billed (the ledger charges 45 s of overhead and a conservative 90 s if no `container_up` event is seen).
* **Resume.** `DONE.json` per model (digest of grid + data manifest + sets); a resumed run with the same `--run-id` skips them.
* **Not covered / open.** (a) The cost gap above. (b) `/update_weights_from_disk` could remove ~100 s of boot per model, but it is not the frozen boot and was not tried. (c) Own-dev splits: `export GRID_OWN_DEV=a,b` AND pass `--own-dev a,b` (files `data/<split>.jsonl`, read with `--tta-choice`, mounted into the image; a mismatch is refused locally). (d) The container disk: two merged copies (~18 GB) + base (9 GB) + grid adapters (~3 GB) are held at once; Modal's default ephemeral disk is assumed large enough. (e) The H100 job cannot reproduce `gate_dev --mode ship` JSONs; those are computed locally from the placed preds.
